# パターンの追加・更新

説明と実装を一組で追加・更新し、読者が仕組みを理解して対応ZIPを取得し、利用・検証できる状態にする。文書の中心は設定値や構造の意味と具体的な動作の説明に置く。実装を作っただけ、文書を書いただけで完了にしない。

## プロジェクトの基準を読む

リポジトリのルートを基準に、次を確認する。テンプレートやレビュー基準をスキル内に複製せず、現在のファイルを正とする。

- [AGENTS.md](../../../AGENTS.md)：配置と作業のルール。
- [追加・更新手順](../../../docs/project/contributing.md)：作成先、画像、ZIPリンク。
- [文書テンプレート](../../../docs/project/templates/index.md.template)：新規文書の出発点。
- [レビュー項目](../../../docs/project/review.md)：説明の質と、注意点が必要になる条件。
- [検証とZIP配布](../../../docs/project/verification.md)：個別検証の規約と配布物の扱い。

## 対象と説明の根拠をそろえる

対象の分野・分類・パターンを特定し、`docs/<分野>/<分類>/<パターン>/index.md`と、対応する`patterns/`の実ファイル・README・検証処理を読む。既存文書の更新では、残すべき説明、公開済みslug、参照元も確認する。

設定名や機能の意味は、対象バージョンの公式仕様と照合する。公式の仕様・推奨、実装から確認した事実、このプロジェクトが選んだ理由を区別する。採用理由が分からなければ既存の判断記録を調べ、分からない部分を推測で既定の方針にしない。

パターン追加・更新の依頼では、対象に必要な文書・実装・README・個別検証を作業範囲に含める。説明だけの修正など範囲が限定されている場合は、その範囲を守り、不足する実装や検証を勝手に補わない。利用者の判断が必要な設定値や採用理由は、実装や記録で確定できる事項と分けて確認する。

## 実装と個別検証を整える

追加では文書と実装に同じ相対パスを使い、更新では既存の動作や公開URLへの影響を確認する。実装の依存関係をサイト本体から分離し、利用先へ持ち込める実ファイルを用意する。配布用コードをサイト自身の実行コードとして直接読み込まない。

プロジェクト直下の`scripts/`には、配置確認・文書検証・ZIP生成などプロジェクト全体に影響する共通スクリプトだけを置く。個別パターン専用の処理は`patterns/<分野>/<分類>/<パターン>/`内に置き、ZIP単体で動くようにする。実行場所がルートであることや、CIから呼ばれることを共通処理と判断する理由にしない。新しいスクリプトを追加する前に、既存の共通スクリプトや対象ツールのコマンドで代替できるか確認する。個別処理のために共通スクリプトへ特定パターンの分岐を追加しない。

プロジェクト直下の`tests/`には、管理スクリプト・掲載サイト・検索・ZIP配布などプロジェクト全体の共通機能に対するテストと、その補助処理・fixtureだけを置く。個別パターン専用のテストは`patterns/<分野>/<分類>/<パターン>/`内に置き、ZIP単体で検証できるようにする。共通機能のテストはfixtureで確認し、特定の実用パターンの文言・設定・収録ファイルへ依存させない。既存テストと目的が重複する場合は、単に移動して残すのではなく、確認範囲を整理する。

実装側にREADME、必要なコード・設定、依存関係の定義、個別検証をそろえる。ロックファイルを使える環境では併せて管理する。設定ファイル名や配置先は対象ツールの仕様と照合し、文書の例と実ファイルを一致させる。

検証には対象の言語・ツールに合ったコマンドを使う。テスト本体の名前や利用ツールは統一しない。READMEに必要な環境・準備・実行場所・検証コマンド・期待結果を書き、必要なテスト・設定ファイルをZIPに含める。準備に失敗したら後続を実行しない。追加時はパターンのルートに`ci.json`を用意し、準備・検証コマンドと必要な実行環境を明示する。共通CIが読み込むため、パターンごとのジョブをワークフローに追加しない。新しい実行環境への対応が必要な場合だけ共通CIを拡張する。

正常例の実行だけでなく、違反検出の設定なら代表的な違反を検出することも確認する。動作に影響する変更では、変更前後の期待結果を対応付ける。単にログを出すだけの処理を検証として済ませない。

## 全体像から細部へ書く

新規文書はテンプレートを使い、更新では既存の有効な説明を保ちながら不足を補う。以下の流れを基本に、対象に合う見出しで構成する。

1. 何のパターンか。対象を理解するために必要な背景を短く説明する。
2. 設定・実装の全体像。ディレクトリマップ、主要ファイルの役割、処理や設定のつながりを示す。
3. 設定値や構造の意味と具体的な動作。ここを文書の中心として、意味のまとまりごとに説明する。
4. 導入・使用方法。必要な環境、依存関係、配置先、実行場所とコマンド、使用例を示す。
5. 必要な場合だけ制約・例外・注意点を説明する。
6. 検証方法と結果。確認日、環境、期待結果、実際の結果、未確認事項を区別する。
7. 参考資料と、そのパターンのZIPへのリンクを置く。

「使う条件・使わない条件」を独立した必須節として追加しない。文書を表や箇条書きだけで埋めず、前の説明を受けて次の説明に進む文章にする。見出しの文言より、読者が理解できる順序を優先する。

## 設定値・構造の説明を具体化する

対象パターンの全設定項目を実ファイルと照合し、各項目について「なぜこの値を選んだのか」「この値にするとどう動くのか」を説明する。代表例だけで済ませず、OSSの設定、パターン独自の設定、コード側で補う既定値も確認する。未設定を選んでいる項目は、省略した理由と省略時の動作を説明する。採用理由が記録や実装から確認できない場合は、もっともらしい理由を作らず、確認できた動作と分けて扱う。

読みやすさと分かりやすさを目的に、設定ごとの説明の境界が分かるよう、見出し・段落・コードの区切りを選ぶ。関連する設定は一緒に説明してよいが、それぞれの採用理由と動作を読み取れるようにする。一律の「理由」「動作」欄や項目ごとの固定テンプレートを必須にしない。テンプレートは出発点であり、形式をそろえるために説明の流れを崩さない。

設定台帳とsetupスキルを提供するパターンでは、台帳の網羅性と利用者への質問量を分ける。項目を「重要」「普通」「あまり見なくてよい項目」に分類し、分類理由も管理する。開始時に「重要のみ」「重要＋普通」「すべて」から質問範囲を選べるようにする。範囲外は現在値・未設定時の既定動作を維持し、個別確認済みと区別して記録する。無効な機能の詳細や同じ設定の型分岐を繰り返し質問せず、有効化・変更が必要になった項目は追加で確認する。分類・スキル・CLIの絞り込み・回答検証・READMEをそろえ、省略した項目が無断変更されないことも検証する。

各まとまりでは、まず対象のファイル名とコードを示す。設定は親キーを含め、関数や構造は関係を理解できる範囲を含める。文脈のない値や1行だけを抜き出さない。

コードに続く文章で、次をつなげて説明する。

- 何を指定・定義する箇所か。
- その値や構造によって、実際にどのような動作・結果になるか。
- どこから読み込まれ、何を受け取り、どこへ渡されるか。
- なぜこのパターンでその値や構造を採用するか。

項目名の和訳や「この設定を有効にする」だけで終えない。例えば自動生成の設定なら、何を入力として読み、ファイルを追加すると何が表示され、何を手動管理する必要がなくなるかまで説明する。

具体例は実ファイルの名前・値と対応させ、入力や操作から結果へつなげる。観測していない結果は「期待する結果」として説明し、実測・確認済みの結果にしない。複数項目が同じ動作を形作る場合は一緒に説明し、逆に異なる役割を一つの長い説明へ詰め込まない。

## 注意点・画像・READMEを扱う

注意点は、環境やバージョン差、入力制限、通常と異なる動作、既存ファイルへの影響、利用先で必要な変更、未確認条件がある場合に限って記載する。条件、具体的な影響、必要な対応まで示す。該当しなければ節を省略し、個別設定の近くに書く方が分かりやすい場合はそこに含める。

画像は構造や流れを文章・コードだけでは追いにくい場合に使う。対象文書の`images/<内容が分かる名前>.png`へ配置し、相対参照と代替テキストを付ける。PNG以外のファイルを改名して済ませない。画像の前後で何を見る図かを説明し、本文・実装と内容を一致させる。

`index.md`はサイト上の詳しい説明、実装側の`README.md`はZIP単体で使うための手順。[READMEテンプレート](../../../docs/project/templates/README.md.template)を使い、環境・導入・使用・検証手順に絞って整える。サイト本文を丸ごと複製しない。

## 配布・サイト・検証まで確認する

トップページの一覧は文書のメタデータから自動生成する。紹介の特徴・表示順・任意の画像は文書先頭の`pattern`へ指定し、ページのTSXへ個別の紹介を追加しない。タイトル・説明・slug・カテゴリ名を二重管理せず、IDの検証とパス生成には共通の`scripts/lib/patterns.mjs`を使う。設定形式は追加・更新手順を参照する。

`title`・`description`・`slug`、本文、コード例、画像、参考資料、ZIPリンクを実ファイルと照合する。ZIPリンクは`/downloads/patterns/<分野>/<分類>/<パターン>.zip`とし、別パターンへのリンクや作業者のローカル絶対パスを公開本文に残さない。記入欄や内部の作業経緯を完成文書に残さない。

ZIPは`static/downloads/patterns/<分野>/<分類>/<パターン>.zip`へスクリプトで生成し、手動編集・コミットしない。生成物を消して不足を隠したり、古いZIPで新しい実装を確認したことにしたりしない。改名・削除が依頼された場合は文書と実装、参照元、古いZIPの除去まで確認する。

ルートから、対象に必要な環境を用意して以下を実行する。

```sh
npm run check:dir
npm run check:docs
npm test
npm run typecheck
npm run build
npm run test:e2e
```

個別検証は生成ZIPを別の場所へ展開し、READMEの準備・検証手順で行う。1つのコマンドで検証できる場合は`npm run verify:patterns -- --id <分野>/<分類>/<パターン> -- <コマンド> <引数>`も使える。共通変更では影響する各パターンを、それぞれの手順で確認する。リポジトリにしかないファイルへの依存、失敗・未実施・時間切れを成功にしない。

実際の対象文書をサイトで開き、ヘッダー・サイドバーからの導線、本文とコードの表示、PNG、ZIPの取得と内容を確認する。自動E2Eのfixtureが成功しただけで、自分が追加・更新したパターンの表示や動作まで確認したことにしない。生成物は直接直さず、元の文書・実装・設定を修正して再生成する。

自動検証が通っても、意味・動作・関係・理由を説明できているかをレビュー項目で読み直す。ルール自体を変えた場合は、追加手順、テンプレート、チェックリスト、スキル、スクリプト、テストの整合も確認する。

## 結果を報告する

不足は該当箇所を直し、再確認する。実行できない確認は理由と再現方法を報告する。文書に確認日・環境・期待結果・実際の結果・未確認事項を残し、サイトビルドの成功、対象実装の成功、人間の確認待ちを分ける。

報告は対象パターン、変更した動作と説明、実施した検証と結果、成果物の確認先、残事項を中心に書く。作業者のローカル絶対パスは報告に使い、公開本文には残さない。コミット・push・PR作成・Issue投稿・クローズ・サイト公開は、明示的に依頼された場合だけ行う。
