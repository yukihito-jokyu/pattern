# 気持ち良いUIモーション

操作の認識、変化の理解、結果、操作の自由をつなぐ。「待たせない」は次の操作を演出完了で止めないこと。通常時の開閉アニメーションを消す意味にしない。遊び心は基本品質を満たした後に加える。[判断基準](references/principles.md)と[ルール](references/rules.md)を使う。

この基盤内ではAGENTS.mdのコマンドと配置に従う。別のリポジトリへ導入した場合は、利用先のAGENTS.md・既存スキルを先に読み、仕様・検証用アプリ・設計履歴を禁止しているリポジトリへ追加しない。作業用仕様と検証は外部一時ディレクトリへ置ける。パスの `<skill>` はこのSKILL.mdのディレクトリを指す。

## 1. 依頼をパターンに振り分ける

| 依頼 | references/patterns.mdの節 |
|---|---|
| 押下、受理、手応え | 1 |
| 保存、通信、処理中、成功・失敗 | 2 |
| 選択、Tabs、並べ替え、段階移動 | 3 |
| 開閉、画面遷移、通知 | 4 |
| 実際のデザインシステムへ適用 | 5 |

複数なら上から該当分を扱う。表にない演出は、利用者の意図と既存部品から不要かを検討する。新エンジンを発明せず、既存recipeへ写せない理由と候補を報告する。

## 2. 依頼から決まらない値

| 値 | 影響 | 既定 |
|---|---|---|
| システム | Token・API | 既存導入を調査。両方/不明なら対象だけ確認 |
| id | 仕様の場所 | 指定の識別名。指定なしはrecipe名。既存idとの衝突時は上書きせず確認 |
| frequency | 反復の強さ | frequent |
| delight | 成功の装飾 | false |
| intent | 意味の評価 | 依頼の目的を1文で書く。目的を特定できなければ確認 |
| labels | 結果の伝達 | 指定文言をそのまま使用。指定なしはnewの既定から実UIに合わせる |
| 時間・曲線 | 一貫性 | 既存正本のToken。独自の80〜400msを上書きしない |

実装方式・既存値が調査で決まる事項は質問にしない。人間の業務判断が必要な点だけ確認する。

## 3. 書く前に読む

- [patterns.md](references/patterns.md)の該当節と見本。
- [design-system.md](references/design-system.md)：new-york/cobaltの識別、正本、Portal・停止・propsの差。
- [principles.md](references/principles.md)：目的と6原則。数値を規格化しない。
- [rules.md](references/rules.md)：STR/DEP/NAM/CODE/ERRと該当するSTATE/ASYNC/MOT。
- 利用先の実ファイル・Story・配布定義。調査時点の参照先だけで現在の状態を断定しない。

## 4. 作る順序

1. 対象の操作→受理→処理状態→結果と、次にできることを書き出す。状態を演出の完了から決めない。
2. 本基盤の仕様追加なら `node <skill>/scripts/motion.mjs new ID SYSTEM RECIPE` で始める。編集はmotion.jsonだけ。対象リポジトリに仕様を保存できない場合は外部一時ディレクトリで同じコマンドを使う。
3. intent/frequency/delight/labelsを決め、`node <skill>/scripts/motion.mjs fmt`と`build`を実行する。対象から決まらない文言の根拠は報告へ書く。
4. 実UIの依頼なら既存部品の状態・Token・機構へ接続する。[実UI手順](references/patterns.md#5-実uiへ接続する)を使い、仕様だけで完了にしない。
5. 操作状態、静止時の寸法、名前付きexport、SVG、キーボード・フォーカスを維持する。

## 5. 検証する

仕様は作業用ディレクトリで `node <skill>/scripts/motion.mjs check`。本基盤では `npm run check` も実行する。型は閉じたJSON schemaで検査し、JSは構文検査と振る舞いテストで確認する。

実UIは利用先の型検査・lint・production buildに加え、連続操作、途中OFF、ON復帰、OS reduce、失敗・再試行、Portal、キーボード、スマホ幅を確認する。ブラウザーの低減設定エミュレーションを実機OS検証と混同しない。

失敗はルールIDから直す。設定緩和・抑止コメント・テスト削除で通さない（TOOL-02）。

## 6. 完了前チェックリスト

- [ ] STATE-01/MOT-01：実際の処理結果とラベル・状態通知が一致する。
- [ ] MOT-02：実コードが対象の正本Tokenを参照する。仕様の生成CSSは適用の代わりではない。
- [ ] ASYNC-01/MOT-03/MOT-05：開く・閉じる両方の中間状態、途中反転、演出中の別操作、停止・再開・フォーカスを実操作した。
- [ ] MOT-04/MOT-06：遊び心の頻度と対象の同一性を確認した。
- [ ] PROC-01：仕様と生成物、変更した正本と配布・Story・利用スキルを照合した。
- [ ] TEST-01/MOT-07：未観測の性能や快適さを断定していない。

## 7. 報告する

作ったもの、変更ファイル、採った既定値と理由、検証対象・コマンド・結果、未実施と人間の確認待ちの順で書く。コードの実際の記述と場所を示す。Issue投稿・公開は依頼された範囲だけ行う。
