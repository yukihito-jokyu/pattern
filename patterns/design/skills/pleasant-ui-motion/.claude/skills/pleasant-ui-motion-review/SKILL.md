# モーションのレビュー

実装スキルの[携帯用ルール](../pleasant-ui-motion/references/rules.md)を正とする。基盤内ではdocs/design/rules.mdと同内容。一般のUI制作へ勝手に作業を広げず、指定された差分を読む。

## 1. 対象を決める

指定されたファイル・PR・差分を対象にする。指定なしは未コミット差分と未追跡ファイルを読み、無ければ基準ブランチとの差分を読む。変更した説明・検証報告・既定値・未使用の参照コードも対象に含める。仕様の形式と実UIの妥当性を分ける。

## 2. 機械の検査を回す

基盤ならnpm run check。利用先ならそのAGENTSとpackage.jsonに従い、型・lint・buildと対象の操作テストを回す。仕様は実装スキルのscripts/motion.mjs checkで検査する。失敗はIDと出力を載せ、同じ内容を手動指摘として重複させない。検査を実行できなければ未実施と理由を示す。

## 3. 抜け道を確かめる

| ルールID | 確認方法 | 違反例 |
|---|---|---|
| TOOL-02 | manifestのprotectedに当たる変更を依頼範囲と照合。検査を通すための変更・skip・抑止を指摘する | 参照実装を検査から除外 |
| DEP-02 | package/lockと既存部品の利用箇所を照合する | 演出のため別のmotionエンジンを追加 |

基盤の保守として明示的に許可された設定変更と、違反を隠す変更を区別する。保護ファイルを触ったという理由だけで、認可済み保守を差し戻さない。

## 4. 機械で拾えないルールを確かめる

| ルールID | 確認方法 | 違反の典型例 |
|---|---|---|
| DEP-02 | 依存差分と対象の既存APIを照合 | 既存Motionを別ライブラリーへ置換 |
| STATE-01 | createSaveの単体/ブラウザーテストと対象の業務処理照合 | animation.finishedで保存成功 |
| TEST-01 | 実行対象・コマンド・観測・未確認範囲を報告と照合 | schema成功だけで全UIが快適と断定 |
| PROC-01 | portable rulesの同期検査と波及レビュー | 配布skillのrules.mdだけを変更 |
| TOOL-02 | guard.py、保護ファイルdiff、hook | @ts-ignore、test.skip、検査の削除 |
| MOT-01 | validateのlabels検査と実UIの意味伝達レビュー | 全状態のラベルを保存しましたにする |
| MOT-02 | 実ファイルのCSS/WAAPIとprofilesの出典を照合。auditで調査時点からのToken差分を確認 | duration:400を全要素に直書き |
| MOT-03 | resolveMotionとブラウザーの途中変更検査、Portalは対象で確認 | 子onでOSのreduceを上書き |
| MOT-04 | validateのdelight条件と実UIの再演レビュー | キー入力ごとに成功の跳ね |
| MOT-05 | 通常設定で開く・閉じる両方の中間状態を観測し、途中反転と演出中の別操作、論理状態・フォーカスを確認 | 待機をなくすために即時hiddenへ変更、またはanimation.finishedまで入力をロック |
| MOT-06 | intent、実画面、実際の状態変化を一緒に追う | 無関係なページ間をカード変形で結ぶ |
| MOT-07 | 計測条件・trace・主張の範囲を確認 | rAFが60回なので快適さを実証したと断定 |

実行対象に含まれないintegration例・コメント・報告でも、上表の意味的な違反を見つけたら指摘する。ルールIDの説明を並べるだけでなく、実際の記述と矛盾する期待を示す。

## 5. ファイルをまたぐ対応を確かめる

motion.jsonと生成css/md、ホストの状態と状態ラベル、正本TokenとCSS/WAAPI参照、ProviderとPortal、変更APIとStory・Registry・利用スキルの両側を開く（PROC-01）。対象にないシステムへ同じpropsを追加していないか確認する。未観測の快適さを自動検査から断定しない。

## 6. 出力の形式

対象、機械の検査（成功/失敗/未実施）、指摘表、判定、残事項の順で書く。指摘表は「ルールID / ファイル:行 / 実際の記述 / 問題と直し方」の列を持つ。同じ違反の重複は避け、場所順に並べる。

検査が通り指摘0件なら「承認」、それ以外は「差し戻し」。未実施は確認完了としない。「承認」は確認した範囲の判定であり、人間が快適と確認した意味ではない。ルールにない提案は指摘とは分ける。指摘のないIDを飾りとして列挙しない。
