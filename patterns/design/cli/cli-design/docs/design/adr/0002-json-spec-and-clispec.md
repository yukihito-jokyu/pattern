# 0002 CLI の設計を JSON の仕様で表し、自作の検査ツールで縛る

- 状態：採用
- 関係するルール：STR-01、STR-02、STR-04、DEP-01、CODE-01、TOOL-01、TOOL-03

## 背景

この基盤が揃えたいのは、CLI の実装ではなく「外から見える形」（コマンド、引数、オプション、出力、終了コード、環境変数）である。依頼の言語は決まっておらず（指示：「どの言語でも対応可能とする」）、設計の成果物は特定の言語のコードにできない。

そのため、設計を言語に依存しない形式で書き、その形式を機械で検査する必要がある。検査では、命名・動詞・終了コードの組など、この基盤のルールに固有の判定が要る。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| Markdown の設計書 | 人が読みやすい | 書き方が作者ごとに分かれ、機械で検査できない |
| OpenAPI・JSON Schema など既存のスキーマ | 既存のツールが使える | CLI の概念（位置引数、終了コード、暗黙のオプション）を表せず、拡張のキーが作者ごとに分かれる |
| 既存の CLI 定義の形式（docopt、各フレームワークの定義） | 実装に近い | 特定の言語・ライブラリに結び付く（DEP-04 の「標準ライブラリだけ」と両立しない） |
| 独自の JSON の形式と、Python の標準ライブラリだけで書いた検査ツール | キーを全部書かせ、ルール固有の判定（NAM-04、ERR-01 など）を表で書ける | 形式と検査ツールを自分で保守する |

## 決定

独自の JSON の形式（`specs/<name>/cli.json`。キーの表は rules.md の CODE-01）と、検査ツール `tools/clispec`（check、fmt、gen、new、command、release、conform）を採る。

## 理由

- JSON はどの言語の標準ライブラリでも読めるため、実装者が仕様を読む手段を選ばない
- 省略できるキーを無くし（CODE-01）、キーの順を formatter に任せれば（TOOL-01）、同じ設計は同じ文字列になる
- JSON にはコメントが無く、検査ツールが表に無いキーをエラーにする（TOOL-03）ため、仕様の中に検査を黙らせる書き方が存在しない
- ルールの表（`tools/clispec/vocab.py`）を rules.md の表と1対1にできる

## 影響

- 仕様の形式を変えるときは、PROC-04 の順（ADR → rules.md → `tools/clispec` と probes.json → 見本の仕様と実装）で変える
- 実装者は `cli.json` ではなく、生成された `cli.md` を読んで実装する（ヘルプの文面がそこにある。ADR 0005）
