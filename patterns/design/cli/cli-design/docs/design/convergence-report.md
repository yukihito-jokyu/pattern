# cli-design 収束テストの記録

独立エージェント（この基盤の作成時の会話履歴を持たないセッション）に同じ課題を解かせ、書き方の違い（揺れ）を測った記録である。手順の詳細は、作成に使ったスキルの convergence-test.md にある。各ラウンドの生データは `.foundation/convergence/round-<R>/` にある。

## 条件

| 項目 | 値 |
|---|---|
| 実行方法 | `claude -p`（Claude Code 2.1.296、モデル claude-opus-5-5）。`--permission-mode acceptEdits`、`--allowedTools` は `Skill`・`Bash(make *)`・`Bash(git diff *)`・`Bash(git status *)`。コピーの CLAUDE.md・スキル・hooks が読み込まれる。利用者のグローバル設定（`~/.claude/CLAUDE.md`：日本語で報告する、コミットの前に計画を出す など）も読み込まれたが、仕様の中身には影響しない |
| エージェントの人数 | 3人（課題ごと）。並列 3、1セッションの上限 1800 秒 |
| 課題 | `.foundation/convergence/tasks.json` |
| 合格基準 | files 1.0、names 0.8 以上、check は全員通過、保護ファイルの変更なし、R1〜R6 の未対処が0件、レビュー検出率 100% |

## ラウンド 1

9人全員が、課題ごとに同じ2ファイル（`cli.json` と `cli.md`）に同じ差分を書いた。T3 では、依頼が「指定した日まで」の片側だけでも、全員が `--due-date-from` と `--due-date-to` を組で置いた（NAM-07 と既定値表のとおり）。費用は9セッションで 9.24 USD だった。

仕様の差分には揺れが無かった。一方で、報告の「決めきれなかったこと」に、仕様に書く場所が無く実装に任される点が共通して挙がった。仕様の形は揃っても、実装の振る舞いが作者ごとに分かれる軸なので、揺れとして扱った。

### 揺れと分類

| # | 課題 | 揺れ | 分類 | 対処 |
|---|---|---|---|---|
| 1 | T1（2人）、T2（3人）、T3（3人） | 絞り込みの繰り返し（AND か OR か）、`edit` のリストの値（置き換えか追加か）、`null` の並び順と範囲の絞り込みでの扱いが決まっていない | R1 軸が決まっていない | 軸 X5 と STATE-02（標準の動詞の振る舞いの決定表）を足し、`tools/clispec conform` で確かめるようにした。probe STATE-02-a〜c。ADR 0007 |
| 2 | T2（3人）、T3（1人） | 空を許す項目を `edit` で空に戻す方法が無い | R1 軸が決まっていない | NAM-07 の `edit` の行に `--clear-<項目>`（`nullable`・`list`・`boolean` の項目）を足し、生成器が置くようにした。probe NAM-07-d。ADR 0007 |
| 3 | T1（2人） | 生成された summary が `Url of the bookmark` になる（揺れではなく、全員が同じ文になった） | — | CODE-04 で、`id`・`url`・`json` を summary の中で `ID`・`URL`・`JSON` にするようにした |

## ラウンド 2（最終ラウンド）

ラウンド1の対処（STATE-02、`--clear-<項目>`、summary の頭字語）を入れた基盤で、ホールドアウト課題 H1 を加えて12セッションを実行した。費用は 13.45 USD だった。4課題とも、3人が同じファイルに同じ差分を書いた。T2 では、生成器が `tag edit` に `--clear-color` を自動で置き、T3 では `note edit` に `--clear-due-date` を置いた。H1 では、3人とも `count-lines`、型 `line_count`（`count`・`path`）、`--skip-empty`、`output.kind` が `list` の同じ仕様を書いた。

仕様の差分に揺れは無かった。報告に挙がった点を次のとおり分類した。

| # | 課題 | 報告に挙がった点 | 分類 | 対処 |
|---|---|---|---|---|
| 4 | H1（2人） | パターン2の手順が `TODO` に `-o/--output` を挙げる一方、AGENTS.md は依頼に無いオプションを禁じている（3人とも置かなかった） | R2 ルールがあいまい | パターン2の手順と既定値表を「依頼が結果をファイルに書くことを求めたときだけ `-o/--output`」に直した |

## レビュー検出率

最終ラウンドで、9件の違反を仕込んだ差分（`.foundation/convergence/review-seeds.json`）を、3人の独立エージェントにレビューさせた。仕込んだ違反は TOOL-03（Makefile から guard を外す、テストを skip する）、STR-04、DEP-02、DEP-05、STATE-01、NAM-02、CODE-02、PROC-06 で、どれも `make check` を通る形にした。費用は 4.72 USD だった。

| エージェント | 検出率 | 余計な指摘 | 判定 |
|---|---|---|---|
| review/agent-1 | 100%（8/8） | 指摘の表には無い。機械の検査の節で OPS-05 の FAIL を引用し、提案の節で STR-01・PROC-04 などに触れた | 差し戻し |
| review/agent-2 | 100%（8/8） | 同上 | 差し戻し |
| review/agent-3 | 100%（8/8） | 同上 | 差し戻し |

3人が検出したルールIDの集合は一致した。3人とも、外された guard と skip されたテストを手で回し直し、「make check が通ったのは検査が外されていたから」と指摘した。

3人が共通して出した「ルール追加の提案」は次の3つである。

| 提案 | 扱い |
|---|---|
| 基盤の直下に置いてよいものが決まっておらず、`examples/` が検査を通る | STR-01 に基盤の直下の名前の表を足し、`tools/clispec check` で確かめるようにした（probe STR-01-c） |
| 保護ファイルの変更を機械で見つけられない（Makefile を変えれば検査ごと外せる） | 実装していない。保護ファイルのハッシュを manifest に持って check で照合する案は、ルールを変えるたびにハッシュを更新する手順が増える。今は hooks（編集前の確認）とレビュー用スキルで守っている。ユーザーの判断に回した |
| 見本の仕様（`specs/notes`・`specs/count-words`）を変えてよい条件が決まっていない | 実装していない。見本を保護ファイルにすると、「notes に期限を足して」のような練習の依頼ができなくなる。ユーザーの判断に回した |

## 最終ラウンドの後に入れた変更

#4・#5 と、STR-01 の基盤の直下の検査は、最終ラウンドの後に入れたので、独立エージェントで測り直していない。どれも、エージェントが既に揃って選んでいた答えを文書に合わせたか、エージェントが触れなかった場所の検査を足したものである。check、probe（66件）、rules_check は通っている。

## 結論

合格基準を満たした。

- 最終ラウンドで、ホールドアウトを含む全課題の files・names・content が 1.000、全員の出力が check を通った。保護ファイルを変えたエージェントはいなかった
- R1〜R6 の未対処は0件である。R6 の #6 は、CLI に固有の意味で、依頼文で決めるものと分類した
- レビュー検出率は3人とも 100% で、判定（差し戻し）と検出したルールIDの集合が一致した

ユーザーに判断してほしい点が2つ残っている。1つ目は、保護ファイルの変更を機械で見つける仕組みを足すか。2つ目は、仕様の形式に、CLI に固有の意味（空行の定義など）を書く説明文の欄を足すか。
