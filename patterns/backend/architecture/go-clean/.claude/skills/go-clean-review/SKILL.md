# go-clean のコードレビュー

このスキルは、中の 3 つと一緒に使う。どれもこのスキルの中にあり、ほかの文書は読まなくてよい。

- [references/rules.md](references/rules.md)：守るルールの全文とコードのひな形。指摘の出典はこのファイルの節番号（「rules 4」など）で示す
- [references/checklist.md](references/checklist.md)：観点ごとの確かめ方。ルール ID（D01 など）は機械検査の出力と共通
- [checker/](checker/main.go)：ファイルをまたぐ整合性の機械検査（Go のプログラム）

## このレビューの考え方

このプロジェクトのルールは 3 つの層で守られている。レビューも同じ 3 段で行う。

| 段 | 何が止めるか | レビューでやること |
|---|---|---|
| 1 | golangci-lint（`make check`） | 実行して結果を確かめるだけ。lint が止めるものを目で探さない |
| 2 | このスキルの機械検査（`checker/`） | ファイルをまたぐ整合性を検査し、出た指摘を確かめる |
| 3 | 人（あなた）の目 | [references/checklist.md](references/checklist.md) の「目視」の項目を読んで確かめる |

1 と 2 は機械が漏れなく見るので、時間の大半は 3 に使う。3 は、設計の判断やテストの中身のように、構文だけでは決まらないものである。

指摘には必ず根拠を付ける。根拠とは、問題のコードの引用と、ルールの出典（rules.md の該当する節の引用）の 2 つである。出典を示せない指摘は「ルール違反」ではなく「提案」として分けて書く。

レビュー中はコードを直さない。直すのは、ユーザーに頼まれてからにする。

## 1. 対象を決める

1. ユーザーがファイル・ディレクトリ・PR を指定したら、それを対象にする
2. 指定がなく git がある場合は、ベースブランチとの差分を対象にする

   ```sh
   git diff --name-only "$(git merge-base HEAD origin/main)"...HEAD   # ベースは main 以外のこともあるので確かめる
   git status --porcelain                                              # まだコミットしていない変更も含める
   ```
3. 指定がなく git もない場合は、プロジェクト全体を対象にする。全体だと伝えてから始める

対象が決まったら、変わったファイルを層に分け、どの集約に関わるかを書き出す。次に、**一緒に変わっているべきファイル** を足す。このプロジェクトの抜けは、ほとんどがこの「対になるファイルの変え忘れ」で起きるからである。

| 変わったもの | 一緒に変わっているべきもの |
|---|---|
| domain の `errors.go` | `handler/error.go` の `errorMappings`、新しい code なら openapi の `Error` の enum |
| domain の制約（最大長・範囲） | マイグレーションの `VARCHAR(n)` / `CHECK`、openapi の `maxLength` / `minimum` / `maximum` |
| 新しい集約 | マイグレーション、`.golangci.yml` の 2 行、`port.go`、`fake_test.go`、`main.go`、openapi |
| `port.go` | `fake_test.go`、repository などの実装、`main.go` |
| `router.go` | handler、`dto.go`、openapi の paths |
| `dto.go` | openapi の schemas |
| マイグレーション | domain、repository の SQL とエラー変換 |
| `.golangci.yml`・`go.mod`・`Makefile` | 変えてよい理由が依頼にあるか（なければそれ自体が指摘） |
| ルールを変えた | プロジェクトのルール文書、既存のコードの同じ書き方の箇所 |

## 2. 機械で確かめる

プロジェクトのルートで次の 2 つを実行する。`<このスキルのディレクトリ>` は、この SKILL.md があるディレクトリの絶対パスに置き換える（プロジェクトの `.claude/skills/go-clean-review` でも、ホームの `~/.claude/skills/go-clean-review` でもよい）。

```sh
make check
go -C <このスキルのディレクトリ>/checker run . -root "$PWD"
```

- `make check` が通らなければ、それだけで必須の指摘になる。失敗したコマンドと出力の該当部分を報告に貼る
- 機械検査の出力は `重さ ルールID 場所 内容` の形である。ルール ID の意味は [references/checklist.md](references/checklist.md) にある
  - **ERROR** はルール違反である。ただし必ず該当コードを開いて確かめてから指摘にする
  - **WARN** は構文からの推測である。コードを読んで、違反なら指摘にし、違反でなければ「確認して問題なし」に理由を添えて書く
  - 対象外のファイルへの指摘は、元からある問題として報告の最後に分けて書く
- 機械検査が動かない場合（Go がない、ネットワークがなく依存を取れないなど）は、その旨を報告に書き、チェックリストの該当項目を目で確かめる

## 3. 目で確かめる

[references/checklist.md](references/checklist.md) を開き、対象の層の節を **すべて** 読む。各項目には「見る方法」が書いてある。「機械」とある項目は 2 で済んでいるので飛ばし、「目視」の項目を 1 つずつ確かめる。

テストは、対象のメソッドが呼ぶ port と返しうるエラーを書き出し、その経路ごとにケースがあるかを突き合わせる（例：2 つの port を呼ぶなら、それぞれの port のエラーのケースがあるか）。

特に、次の 4 つは機械でも lint でも見つからず、見落とすと本番で問題になる。必ず時間をかける。

1. **トランザクションの範囲**：読んでから書く処理が `TxManager.Do` の中にあるか。同時に更新されたときに上書きされて困るなら、`FOR UPDATE` の取得になっているか
2. **ビジネス判断の置き場所**：handler や usecase に、domain に置くべき判断（値の範囲、状態による可否）が書かれていないか
3. **エラーの行き先**：新しいエラーがどの HTTP ステータスになるかを、domain → usecase → `errorMappings` → openapi の順にたどる。500 になるはずのないエラーが 500 にならないか
4. **テストの中身**：正常、エラーの種類ごと、境界値（上限ちょうどと上限 + 1）を網羅しているか。テストが通ることと、テストが正しいことは別である

## 4. 指摘を確かめる

報告に書く前に、指摘の候補を 1 つずつ確かめる。

1. 該当ファイルの該当行をもう一度開き、引用するコードを写す
2. rules.md から、そのルールが書かれた節を探して引用する。同じ節に例外が書かれていないかも読む（例：rules 10 の `tx.go` のログ、rules 2.4 の集約を足したときの `.golangci.yml` の 2 か所）
3. 重さを決める

| 重さ | 基準 |
|---|---|
| 必須 | ルール違反、バグ、500 やデータ不整合につながるもの、`make check` が通らないもの |
| 推奨 | 規約の型からの逸脱で、動作には影響しないもの（命名、並び順、テストの書き方） |
| 確認 | 仕様が決まらないと判断できないもの（`CASCADE` にするか、`FOR UPDATE` が要るか、上限の値） |

迷いやすいものは、次のように決める。レビュアーによって重さが割れないようにするためである。

- テストの書き方の違反（チェックリストの T02〜T08、T10〜T12）は **推奨** にする。ただし、テストの抜けのせいでバグが見逃されている場合は、そのバグの必須の指摘の中に「このテストがあれば見つかった」と書く（テストの指摘を別に必須にしない）
- 根拠の見えない `ON DELETE CASCADE`、`FOR UPDATE` の有無、仕様にない上限値は **確認** にする。依頼や仕様に反すると分かっている場合だけ必須にする
- 依頼と関係のない変更（X08）は **推奨**。ただし、規約どおりだったコードを規約から外す変更なら、その規約の重さに合わせる
- 1 つの問題は 1 か所にだけ書く。同じ問題を必須と確認の両方に書かない

確かめて違反でなかった候補は捨てる。捨てた候補のうち、機械検査の WARN は「確認して問題なし」に書く。

## 5. 報告する

次の形で書く。見出しの順を変えない。

```markdown
## レビュー結果

対象：<対象の説明（例：main との差分 12 ファイル、order 集約の追加）>
make check：<通った / 失敗（失敗したコマンド）>
機械検査：ERROR <n> 件 / WARN <n> 件（うち指摘にしたもの <n> 件）
指摘：必須 <n> 件 / 推奨 <n> 件 / 確認 <n> 件

### 必須

#### 1. <何が問題かを 1 文で>
[internal/usecase/order.go:42](internal/usecase/order.go#L42)

> （問題のコードの引用）

ルール：rules 3.3

> （ルールの引用）

<なぜ問題か。起きることを具体的に（例：注文者の存在確認と保存の間にユーザーが削除されると、500 になる）>

直し方：
（コード例）

### 推奨
（同じ形）

### 確認
（同じ形。「何が決まれば判断できるか」を書く）

### 確認して問題なしとしたもの
- <観点や WARN>：<問題ないと判断した理由>

### 元からある問題（今回の対象外）
- <あれば>
```

指摘が 0 件のときも、「確認して問題なしとしたもの」に見た観点を並べる。何を見たかが分からないと、0 件が「見ていない」のか「問題がない」のか区別できないからである。
