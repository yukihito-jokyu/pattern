01 · 全体図の読み方

横の主経路は、HTTPリクエストが永続化へ進む実行時の呼び出しです。下側にはUser集約の検証とトランザクション、上側には起動時の配線を置きました。実線は呼び出し、破線は初期化と配線です。レスポンスとエラーは同じ呼び出しスタックを戻ります。

この図の usecase → repository は、port を通した実行時の呼び出しです。Go の import は逆向きで、repository が usecase の interface を実装します。infra が adapter を import して接続することはなく、main が生成した *sql.DB を注入します。

03 · POST /users：作成から応答まで

  1. recoverPanic と logRequest を通り、UserHandler.Create がJSONをdecodeJSONで読みます。ボディ上限は1 MiBで、未知フィールドを拒否します。
  2. Name / Email を CreateUserInput に詰め替え、リクエストの context を usecase へ渡します。
  3. NewEmail が構文を検証し小文字化します。User.New は名前をTrimSpaceし、1〜50文字を検証してUUIDと作成日時を設定します。この時点ではTxを開始していません。
  4. TxManager.Do がTxを開始し、そのTxを含む context で ExistsByEmail を実行します。重複なら ErrEmailAlreadyExists を返し、INSERT は実行しません。
  5. 重複がなければ同じTxでINSERTします。メールのUNIQUE制約が並行作成の競合も防ぎます。
  6. Commit成功後、domain → UserOutput → userResponse と変換して201を返します。失敗はhandlerのerrorMappingsでHTTPへ変換します。

05 · トランザクションとエラーの経路

TxManager と UserRepository は同じ *sql.DB を持ちます。Txを含むcontextをcallbackへ渡し、repositoryのconnが *sql.Tx を選ぶことで、重複確認とINSERTが同じTxに参加します。すでにTxがある場合はcallbackをそのまま実行して合流します。

callbackのエラー、またはCommit失敗ではRollbackを試みます。Rollback失敗はerrors.Joinで元のエラーと結合します。panic時はRollbackを試みて再panicし、HTTPミドルウェアが500へ変換します。この経路では、Rollback失敗のログをrepository側で記録する例外があります。

原因HTTPJSON error.code
JSONのdecode失敗400invalid_request
ID / Name / Emailの検証失敗400invalid_argument
該当ユーザーなし404not_found
メール重複 / SQLSTATE 23505409already_exists
未対応エラー / panic500internal

errors.Isでラップ済みのエラーを判定します。未知エラーは詳細をslogに残し、レスポンスには固定の internal server error を返します。23505の変換は制約名を見ず、すべてのunique violationをメール重複として扱う現実装です。

 25  // Do は fn をトランザクション内で実行する。既にトランザクション中なら合流する。
 26  func (m *TxManager) Do(ctx context.Context, fn func(ctx context.Context) error) (err error) {
 27  	if _, ok := ctx.Value(txKey{}).(*sql.Tx); ok {
 28  		return fn(ctx)
 29  	}
 30  
 31  	tx, err := m.db.BeginTx(ctx, nil)
 32  	if err != nil {
 33  		return fmt.Errorf("begin tx: %w", err)
 34  	}
 35  
 36  	defer func() {
 37  		if p := recover(); p != nil {
 38  			if rbErr := tx.Rollback(); rbErr != nil {
 39  				slog.ErrorContext(ctx, "rollback after panic", "error", rbErr)
 40  			}
 41  
 42  			panic(p)
 43  		}
 44  
 45  		if err == nil {
 46  			return
 47  		}
 48  
 49  		if rbErr := tx.Rollback(); rbErr != nil {
 50  			err = errors.Join(err, fmt.Errorf("rollback: %w", rbErr))
 51  		}
 52  	}()
 53  
 54  	if err = fn(context.WithValue(ctx, txKey{}, tx)); err != nil {
 55  		return err
 56  	}
 57  
 58  	if err = tx.Commit(); err != nil {
 59  		return fmt.Errorf("commit: %w", err)
 60  	}
 61  
 62  	return nil
 63  }

06 · User集約とusersテーブル

列SQLの型・制約domainでの扱い
idUUID · PRIMARY KEYID値オブジェクト。標準uuidで生成・ParseIDで正規化
nameVARCHAR(50) · NOT NULL前後空白を除去、Unicodeの文字数で1〜50を検証
emailVARCHAR(254) · NOT NULL · UNIQUEnet/mailで検証。表示名付きは拒否し、文字列全体を小文字化
created_atTIMESTAMPTZ · NOT NULLusecase.now()をNewへ渡す。SQLに明示的に保存

現時点のマイグレーションはusersの1テーブルで、外部キーや他集約との関係はありません。Reconstructは保存済みデータの復元専用で再検証しません。メール254文字の上限はDB側にあり、NewEmailには同じ長さ制限の明示チェックはありません。
