# 実装手順

正本はdocs/design/rules.md、構造はarchitecture.md、手順はこのスキルのreferences/patterns.md、見本はcourses/go/とlearning-setupである。既存と規則が違えば規則に従い、相違を報告する。

## 1. 依頼をパターンに振り分ける

| 依頼                                           | patterns.md |
| ---------------------------------------------- | ----------- |
| 新しい学習項目、教材追加、練習を足す           | 1           |
| 本文、コード、出力、注目点、出典、対象版を変更 | 2           |
| ビューア、生成器、CLI、スキルを変更            | 3           |

複数に当たれば上から行う。どれにも当たらなければ新しいパターンの提案を報告し、勝手な構造を作らない。

## 2. 依頼から決まらない値

| 値                  | 影響         | 既定値                                 |
| ------------------- | ------------ | -------------------------------------- |
| 言語                | 本文         | 日本語                                 |
| 学習形式            | スライド密度 | 非同期自習                             |
| 枚数                | deck         | 1項目2枚                               |
| 注目表示            | UI初期状態   | ON                                     |
| source確認日/対象版 | 根拠         | 実際に取得した資料から決める。推測不可 |
| 前提                | 順序         | 既存curriculumの先行項目               |

既に依頼と実装から決まる値を聞き直さない。構成が分かれる未確定事項だけを聞く。既定値を使ったら報告する。

## 3. 書く前に読む

1. patterns.mdの該当節。
2. 教材ならSTR/ERR/OPS/PROC、画面ならSTATE/ASYNC/OPS/CODE、基盤ならDEP/TOOLの規則。
3. 見本のprofileとlessonとdeck、または変更するruntime。

## 4. 作る順序

PROC-01：公式資料取得→profileと順序→html-deckの生成器でdeck→lesson本文→注目対象→検査。
保守変更は内側model→render→CLI/画面→対応テストの順。ソースの保存後に対象のPrettierとESLintを回す。course JSONの正規整形もPrettierを使う。単独CLIのformat-fileと所有台帳を書き換えて整形検査へ合わせない。

## 5. 検証する

npm run checkを回す。ルールや設定を緩めず、IDの規則へ戻ってソースを修正する。検査基盤の変更時はrules_checkとviolation_probeを再実行する。

## 6. 完了前チェックリスト

- STR-02：データ追加だけで済む変更をエンジンへ埋め込んでいない。
- DEP-02：保護面と依存変更が依頼範囲とADRに対応する。
- NAM-02：名前と値の役割が一致する。
- CODE-03：公開関数に型と入出力、理由のコメントがある。
- OPS-01：資料本文の取得、対象版と主張を照合した。
- TEST-01：assertが動作を確認し、書込みは一時領域で行う。
- PROC-02：profile⇔lesson⇔deck⇔出力⇔生成スキルが一致する。
- PROC-03：人間の未確認を自動成功と混同しない。
- TOOL-04：npm run checkが成功した。

## 7. 報告する

作ったもの、変更したファイル、既定値と根拠、check結果、失敗・未実施・残事項の順で報告する。
