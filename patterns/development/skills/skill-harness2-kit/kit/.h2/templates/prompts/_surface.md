# 変えてよいもの

スキルは部品の木である。部品ごとに、実行の中での費用と届く範囲が違う。

| パス | 何か | いつ文脈に入るか |
|---|---|---|
| `SKILL.md` の frontmatter の `description` | スキルを使う場面の説明 | 常に。スキルの一覧としてモデルに見え、このスキルを呼ぶかどうかを決める |
| `SKILL.md` の本文 | 手順と規則 | スキルが呼ばれたとき。全文が入り、その後のすべてのターンで場所を取る |
| `references/<名前>.md` | 場面ごとの知識と手順 | 本文が名指しし、モデルが Read で開いたときだけ |
| `scripts/<名前>.py`、`scripts/<名前>.sh` | 決まった操作の補助 | 本文が名指しし、モデルが Bash で動かしたときだけ。文脈に入るのは出力だけ |
| `assets/<名前>` | ひな形や素材 | 本文が名指しし、モデルが使ったときだけ |

間違えやすいのは次の3つである。

`description`：スキルが呼ばれるかどうかを決める唯一の部品である。軌跡で、呼ばれるべき依頼でスキルが呼ばれていない（`[ACTION] Skill` が無い）か、呼ばれるべきでない依頼で呼ばれているときだけ変える。frontmatter の description 以外の行は変えない。

`references/`：本文がファイルの相対パスと読む場面を書かない限り、開かれない。名指しの無い参照ファイルは死んだ部品である。

`scripts/`：実行が自分で組み立てて間違えた、または時間をかけた決まった操作を、確かな手順に置き換える。本文に、いつ、どのコマンドで動かし、出力をどう使うかを書く。

軌跡が変える必要を示したところだけを変える。ただし、どこかを変えるときは、中身と同じくらい形が大事であり、安い形は一見して明らかな形ではない。

本文に文を足すのは高くつく選択である。本文はスキルが呼ばれるたびに全文が文脈に入り、エージェント自身の出力の余地と競う。この仕事で最も高くつく失敗は、余地を使い切るまで考え続けて何も作らない実行であり、文を足すとそれが起きやすくなる。必要なときだけ開かれる部品は、開かれるまで費用がかからない。

だから、次の順で選ぶ。
  - 見分けられる場面があるものは `references/` に置く。文書の種類ごとの手順、形式、繰り返し起きる状況。新しい指示の既定の置き場である
  - 実行が手で組み立てて間違えた、または時間をかけた決まった操作は `scripts/` に置く
  - 実行の中で機械的に繰り返し起きる問題（作った成果物が形式に合っているか、必要なファイルが揃っているか）は、仕上げる前に動かす確かめのスクリプトにし、本文の完了の手順から呼ばせる。文は読み飛ばされうるが、出力を見て直す手順は飛ばされにくく、本文の場所も取らない
  - 本文の文は最後にし、すべての実行に当てはまる短い規則だけにする。足すなら、別の何かを削って払う

提案ごと捨てる3つの規則。検証はどの実行よりも先に動き、落ちた木は丸ごと捨てられる。

1. 参照ファイルには名指しの行が要る。最も破られる規則である。`references/<名前>.md` を作るか残すなら、同じ編集で `SKILL.md` の本文に、その相対パスをそのまま書き、読む場面を添える。

       <この参照ファイルが扱う場面>ときは `references/<名前>.md` を読む。

   名指しの無い参照ファイルはどのみち開かれない。名指しの行が、その部品を存在させる。

2. 動的な挿入を増やさない。`SKILL.md` と参照ファイルの中の、感嘆符とバッククォートで始まるコマンドの記法は、スキルの中身がモデルに渡る前にシェルで実行される。元の木より増やした木は、実行の前に捨てられる。

3. 名指しした全部のパスが木に要る。本文や参照ファイルで名指しした `references/`・`scripts/`・`assets/` のファイルは、同じ提案に入れる。名指しだけしてファイルを置かないと、スキルは存在しないファイルを呼ぶ。

次の場合も捨てられる。上の表のパス（名前は英数字と `.`・`_`・`-`、ディレクトリは1階層）の外のファイルは、どれほどよくても捨てられる。frontmatter の description 以外の行を変えた木、description が空か1024字を超えるか `<`・`>` を含む木、`SKILL.md` が500行を超える木、`.py` が Python としてコンパイルできない木も捨てられる。

成果物の形は依頼のものであり、あなたのものではない。スキルはエージェントがどう働くかを変えるもので、何をどんな形で渡すかを変えてはならない。タスクが項目・列・シート・節・順番を名指ししているなら、その形は依頼の一部である。説明の列を足す、導出を成果物の中で言い直す、分かりやすくするために見出しの名前を変える、確かめられるように途中の値を見せる、とエージェントに指示する部品は成果物を変えている。後で読む人や取り込む仕組みは、名前と位置そのものを手がかりにする。エージェントの考えを見えるようにする手引きは、スキルの文か軌跡に置き、成果物には置かない。タスクが求める値は値として渡す。式、穴埋めの印、説明だけで実行していない計算は、残りの仕事を読み手に押しつける。

# 変え方

スキルは `context/harness/` にあり、あなたが編集してよい。ファイルを開き、普段の道具でその場で変え、新しい部品が正しい手段であれば新しいファイルを作る。ディスク上の編集がそのまま提案である。別の形式で書き直す必要は無く、この返答に書いたことはスキルを変えない。

- 触れなかったファイルは、そのまま引き継がれる。同じ中身に保つために書き直さない
- 部品を消すには、そのファイルを消す
- 証拠がどの変更も支持しないなら、すべてをそのままにし、notes に KEEP_BASE と書く。それは失敗ではなく正当な答えである。証拠が支持しない改変は、文脈を使うだけで何も得ない

それから、`<notes>` の区画を1つだけ返し、ほかには何も書かない。各変更について、それを動機づけた軌跡の場面を書く。notes は人が読むもので、機械が当てはめるものではない。
