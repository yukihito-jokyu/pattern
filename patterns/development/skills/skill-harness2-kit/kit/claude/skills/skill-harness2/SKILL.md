# skill-harness2

このリポジトリにあるスキル1つ（以下、対象スキル）を、harness2 の方法で改善する。手を動かすのは補助 CLI `python3 .h2/h2.py` で、このスキルは CLI の出力を読んで次の手を選び、人に決めてもらう場面で止まる。

## 前提：この方法が何をするか

補助 CLI は、承認したタスクごとに次の5段を回す。各タスクは承認したときのスキル（H0）から始め、前のタスクで分かったことはライブラリを通してだけ後のタスクに伝わる。

1. **基準の実行**：今のスキルを入れた使い捨ての作業場所で、`claude -p` にタスクを k 回解かせる。正否は見ず、スキルがどう振る舞うかの証拠にする
2. **提案**：INV（手順、道具、完了の確かめ方）と DOM（実務家の知識）の2人の編集者が、証拠を読んでスキルの木を直す。壊れた候補は実行の前に検証で落とし、1回だけ差し戻す
3. **試行**：各候補で同じタスクを1回解かせる
4. **合成**：全候補の差分と実行を読み、根拠のある編集だけを1つにまとめる。元のまま（KEEP_BASE）も正しい答えである
5. **選択と振り返り**：完成品の成果物だけを匿名で比べて1つを選び、編集ごとの効果と、次のタスクへ移す教訓を残す

選ばれた候補は、人が `show` の差分を見て `adopt` を実行するまで対象スキルに書き込まれない。

## 人が決める場面

次の場面では AskUserQuestion で聞き、答えを得る前に次のコマンドを実行しない。

| 場面 | 見せるもの | 聞くこと |
|---|---|---|
| 対象を決める | `.claude/skills/` の一覧 | 改善するスキル（`init` の `--skill`）と対象の名前 |
| プロファイルを決める | `references/profile-guide.md` の「人と決める項目」 | 仕事の説明（`work`）、k、モード、モデル、1回あたりの上限 |
| タスクを決める | `references/task-guide.md` の「良いタスク」 | 依頼文と材料。対象スキルが実際に受ける依頼に近いものを2〜5件 |
| 予算を承認する | `check` が書いた `plan.md` の全文 | このラウンドの実行を承認するか（承認なら `approve`） |
| 採用する | `show` の出力の全文と、`references/reading-results.md` の「確かめること」 | 採用する候補（タスクとモード）か「採用しない」か |

承認と採用を、人の代わりに決めない。予算を使う判断と対象スキルを書き換える判断は人が持つ。

## 手順

`<対象>` は対象の名前（小文字・数字・`-`・`_`）である。引数に対象の名前があればそれを使い、無ければ人に聞く。

### A. 準備（初めての対象）

1. 人に対象スキルを聞き、`python3 .h2/h2.py init <対象> --skill <対象スキルのディレクトリ>` を実行する
2. `references/profile-guide.md` を読み、人と決めた値で `.h2/targets/<対象>/profile.json` を書く
3. `references/task-guide.md` を読み、人と決めたタスクを `.h2/targets/<対象>/tasks/<id>/task.md` と `tasks/<id>/workspace/` に書く。事後の検査を使うなら `tasks/<id>/checks.json` も書く
4. `python3 .h2/h2.py check <対象>` を実行する。問題が出たら直して、もう一度 check する
5. `plan.md` を人に見せて承認を聞き、承認されたら `python3 .h2/h2.py approve <対象>` を実行する

### B. 実行

1. `python3 .h2/h2.py run <対象>` を、Bash ツールの `run_in_background: true` で動かす。1タスク・1モードで実行 4k 回と編集のセッション 3k 回を使うので、数十分から数時間かかる
2. 終わりの通知を待つ。途中の様子を聞かれたら `python3 .h2/h2.py status <対象>` を実行して進みを伝える
3. 途中で止まっても、もう一度 `run` を実行すれば終わった実行とセッションを使い回して続きから再開する

### C. 結果を見て採用する

1. `checks.json` を書いたタスクがあれば、`python3 .h2/h2.py judge <対象>` を実行する。結果は人が読む材料で、方法には使われていない
2. `python3 .h2/h2.py show <対象>` を実行し、出力の全文を人に見せる。`references/reading-results.md` の「確かめること」に当たる点があれば添える
3. 採用する候補か「採用しない」かを聞く
4. 採用するなら、`show` が出した採用のコマンド（`python3 .h2/h2.py adopt <対象> --task <id> --mode <モード> --confirm <符号>`）をそのまま実行する。採用できるのは1ラウンドに1つである
5. `git diff` で対象スキルの差分を人に見せる。コミットは人が頼んだときだけ行う

## 繰り返すこと

どの場面でも、迷ったら `python3 .h2/h2.py status <対象>` を実行し、出力の `段階:` と `次:` の行で次の手を選ぶ。`問題:` の行があれば、まずそれを直す。

| `段階:` の値 | すること |
|---|---|
| 準備 | `次:` の行に従う。プロファイルとタスクが無ければ手順 A の2〜4、`問題:` があれば直して check |
| 承認待ち | `plan.md` を人に見せて承認を聞く（手順 A の5）。`問題:` に「変わりました」とあれば check からやり直す |
| 実行待ち | 手順 B の1 |
| 実行中か中断 | 自分が動かした run がまだ動いていれば待つ。止まっていれば手順 B の3 |
| 結果の確認 | 手順 C |
| 採用済み | 採用したことを報告する。続けて改善するなら、新しいタスクを人と決めて check から始める（新しいラウンドになる） |

エラーが出たら `references/troubleshooting.md` で、エラーの文の言葉を探す。

## してはいけないこと

- ラウンドの途中（approve の後、adopt の前）に、対象スキル・`profile.json`・`tasks/` を手で変える。変えると承認と指紋が合わなくなり、run と adopt が止まる
- `profile.json` の `work` などの文と `task.md` に、採点の基準や正解を書く。方法は答えを見ずに改善するもので、答えを入れると改善がタスクへの暗記になる
- `.h2/targets/<対象>/runs/` の下のファイルを手で変える。完了の記録と指紋で再開を判定しているため、記録が実体と食い違う
- `run` の出力や `show` の選択をそのまま採用の判断にする。最後の判断は、人が差分を見て行う
