# タスクの書き方

タスクは、対象スキルを改善するときに使う依頼である。1つのタスクは `.h2/targets/<対象>/tasks/<id>/` に置き、`<id>` は小文字・数字・`-`・`_` の64文字以内にする。

```text
tasks/<id>/
├── task.md        依頼文（必須）
├── workspace/     仕事の材料（任意）。実行のたびに使い捨ての作業場所へ写す
└── checks.json    事後の検査（任意）。judge だけが読み、改善には使わない
```

## 前提：タスクがどう使われるか

各タスクは、承認したときのスキルから改善を始める。前のタスクで選ばれたスキルと教訓はライブラリに残り、後のタスクの編集者が「確かめ直す仮説」として読む。そのため、改善が1つのタスクに偏らないよう、対象スキルが実際に受ける依頼に近いものを、種類を変えて2〜5件用意する。

## 良いタスク

- 対象スキルが受け持つ依頼で、利用者が実際に書きそうな文である
- 材料（`workspace/`）だけで解ける。外部のサービスや、作業場所の外のファイルに頼らない
- 成果物の形（ファイル名、見出し、列）が依頼文に書いてある。選択役は依頼文に書かれた形への適合で比べる
- 1回の実行が `rollout.timeout_sec` の中で終わる大きさである

## task.md

依頼文そのものを書く。実行のときに `claude -p` へ標準入力で渡る。

対象スキルの frontmatter に `disable-model-invocation: true` がある（人が `/名前` で呼ぶスキルである）なら、task.md の先頭の語を `/<スキルのディレクトリ名>` にする。そうしないと実行の中でスキルが呼ばれず、編集が何も変えない。`/名前` で始めた実行では stream に Skill の呼び出しが出ないため、補助 CLI は依頼文の先頭の語で「呼ばれた」と数える。

```text
/minutes-format
raw.md の議事録を整え、formatted.md に書いてください。
```

## workspace/

材料を置く。実行のときは `workspace/` の中身がそのまま作業場所の直下になる。`.claude/` と `.git/` は写さない。対象スキルは補助 CLI が作業場所の `.claude/skills/<名前>/` に入れる。

材料に答えを置かない。模範解答や期待する出力を置くと、改善がその答えへの暗記になる。どうしても同じ場所に置くなら、そのパターンを profile.json の `leak_globs` に書く。`leak_globs` に当たるファイルは証拠に写らず、材料にあれば check が拒む。

## checks.json（任意）

選択の後に、人が採否を決める材料として成果物を確かめるコマンドである。改善の方法（提案・合成・選択）には使わない。

```json
{
  "checks": [
    {"name": "見出しがそろっている", "command": "grep -q '^## 決定事項' {task_dir}/formatted.md", "timeout_sec": 30}
  ]
}
```

- `{task_dir}` は実行の後の作業場所、`{reply_file}` は最後の返答を書いたファイルに置き換わる
- コマンドが終了コード 0 なら通った、0 以外なら落ちた、時間切れか起動できなければ未判定になる
- `/bin/sh -c` で動くので、使うコマンドは利用者の機械にあるものにする

## 書いた後

`python3 .h2/h2.py check <対象>` を実行する。task.md と材料に採点の印や `leak_globs` に当たるものがあると、check が拒む。
