# show の読み方

`python3 .h2/h2.py show <対象>` は、タスクとモードの組ごとに1つの節を出す。人はこの出力で、採用する候補か「採用しない」かを決める。

## 前提：選ばれた候補は「たぶん良い」でしかない

選択役は完成品の成果物だけを匿名で比べて選ぶ。実行は各候補で1回だけなので、ばらつきで良く見えた候補が選ばれることがある。harness2 の論文の失敗の分析では、退行の原因は (1) 選択が弱い候補を選んだ、(2) 誤った前提が全候補に広がった、(3) ばらつきで切り分けられない、の3つだった。そのため、採否は人が差分を読んで決める。

## 節の中身

| 見出し・行 | 意味 |
|---|---|
| 選ばれた候補 | 完成品のラベル（並列モードは `agg<i>`、逐次モードは `c<t>`）と、選択役に見せた匿名の ID |
| 選び方 | 選択役が選んだか、k = 1 で起動しなかったか、選択役が失敗して並べた最初の完成品にしたか |
| 元のスキルからの変化 | 追加・変更・削除したファイルの数。「変化なし」は KEEP_BASE の完成品が選ばれたこと |
| 確認の符号、採用のコマンド | adopt に渡す値。符号は選ばれた木の指紋の先頭12文字で、木が記録と違えば adopt が止まる |
| 選んだ理由 | 選択役の `<why>`。決め手と次点の候補が書いてある |
| 元のスキルとの差分 | 承認したときのスキルから選ばれた木への unified diff |
| 合成の notes | 合成役の1行ずつの判断。`kept` / `revised` / `dropped` -> どの編集 -> 根拠（何回の実行で何が起きたか） |
| 振り返り | 編集ごとの効果。`helped`、`hurt`、`no observed effect`、`confounded`（切り分けられない） |
| 移せる教訓 | 振り返り役が後のタスクに移せる教訓を書いたか。書いた場合だけライブラリに残る |
| 台帳 | 実行 R = 4k、編集のセッション P = 3k の数。合わないと run が止まるので、出ていれば合っている |
| 多様性 | 完成品どうしの行の重なりの平均。1.0 に近いほど完成品が同じ本文に潰れている |
| 落ちて入力の木に戻った段 | 検証に2回落ちたか、セッションが失敗した段（fell_back） |
| 基準の実行と完成品 | 実行ごとの成果物の有無、スキルが呼ばれたか、ターン数、終わり方、費用 |

## 確かめること

次に当たる点があれば、採否を聞くときに人に添える。

1. **スキルが呼ばれていない**：基準の実行の「スキルの呼び出し」が「なし」なら、本文と参照ファイルの編集はその実行に効いていない。task.md の先頭を `/名前` にするか（`task-guide.md`）、`description` の変更が要る
2. **全候補が同じ前提に立っている**：差分と合成の notes を読み、すべての編集が同じ思い込み（たとえば材料の読み違い）に立っていないか。全候補が同じなら、一致は独立した証拠ではない
3. **根拠が1回の実行だけ**：合成の notes の根拠が「1/2」のように1回の実行だけなら、ばらつきの可能性がある
4. **成果物の形を変えている**：差分が、見出しや列の名前、出力の順番を変える指示を足していないか。成果物の形は依頼のもので、スキルが変えてよいものではない
5. **基準より悪い**：`judge` の結果で、選ばれた完成品が基準の実行より多く落ちていないか（judge は改善には使っていない。人の判断の材料である）
6. **費用**：「このモードの費用」が承認した上限に比べて大きすぎないか

## 採用しないとき

何もしない。対象スキルは変わらない。続けて改善するなら、タスクやプロファイルを見直して `check` からやり直す（新しいラウンドになる）。
