# 0007 各タスクは承認時のスキルから始め、採用は人が1つを選ぶ

- 状態：採用
- 関係するルール：PROC-07、OPS-04、STATE-04

## 背景

harness2 は、タスクの流れの中で各タスクを元の harness から始め、前のタスクで分かったことをライブラリ（選ばれた木と教訓）で後のタスクに渡す（`schedule.run_domain`）。正否は事後の採点でだけ測り、方法には使わない。この基盤は利用者の1つのスキルを直すので、最後に「どの木を対象スキルに書き込むか」を決める必要がある。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 前のタスクの選ばれた木を次のタスクの入力にする（木を連鎖させる） | 改善が積み上がる | harness2 の方法と違う。1つのタスクの過学習が後の全タスクに伝わる |
| 各タスクを承認時のスキル（H0）から始め、ライブラリで教訓を渡し、採用は人が show を見て1つを選ぶ | harness2 と同じ。採否の判断が人に残る | タスクの数だけ候補ができ、人が選ぶ手間がかかる |
| 事後の検査の結果で自動で採用する | 人の手間が無い | 測定が方法に入る（STATE-04 に反する）。論文の失敗の分析にある「誤った前提の広がり」を人が見る機会が無い |

## 決定

2つ目を採る。`run` は全タスクを H0 から改善し、`show` が各タスク・モードの選ばれた木、差分、根拠を並べる。人は AskUserQuestion で1つを選ぶか「採用しない」を選び、`adopt --confirm <符号>` で対象スキルに書き込む。後のタスクほどライブラリの教訓を多く持つので、`show` は最後のタスクを先頭に並べる。

## 理由

harness2 の方法に忠実であることと、スキルを書き換える判断を人に残すことの両方を満たすからである。`judge` は採用の判断材料として任意で使えるが、方法（提案・合成・選択）には入らない。

## 影響

- 採用した後は対象スキルの指紋が変わるので、次のラウンドは `check` と `approve` からやり直す
- 木を連鎖させる改善が欲しくなったら、この ADR を置き換え、`execution` のタスクの入力の木と `plan.md` の説明を変える
