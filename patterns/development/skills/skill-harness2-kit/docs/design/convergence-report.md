# skill-harness2-kit 収束テストの記録

独立エージェント（この基盤の作成時の会話履歴を持たないセッション）に同じ課題を解かせ、書き方の違い（揺れ）を測った記録である。手順の詳細は、作成に使ったスキルの convergence-test.md にある。各ラウンドの生データは `.foundation/convergence/round-<R>/` にある。

## 条件

| 項目 | 値 |
|---|---|
| 実行方法 | `claude -p`（Claude Code 2.1.308）。基盤のコピーごとに1セッションを起動し、`--permission-mode acceptEdits --no-session-persistence` と、`make *`・`python3 *`・`git diff *` などの読み取りと検査のコマンドだけを `--allowedTools` で許した。コピーの CLAUDE.md・スキル・hooks はそのまま働く |
| エージェントの人数 | 3人（3並列、1セッションの上限 1800 秒） |
| 課題 | `.foundation/convergence/tasks.json`（T1-add：代わりのモデルを profile.json で決める、T2-change：提案役の指示にスキルの名前を入れる、T3-cross：show に judge の結果を出す、H1-holdout：採用の履歴を見るコマンド） |
| 合格基準 | files 1.0、names 0.8 以上、全員の出力が check を通る、保護ファイルを変えない、R1〜R6 の未対処が0件、レビュー検出率が全員 100% |

## ラウンド 1

費用は9セッションで $22.05（runner が報告した値）だった。

T1 と T2 は、3人とも同じファイルの集合を変え、中心の名前（T1 の `fallback_model`、T2 の `skill_name`）も同じだった。names が低いのは、テスト関数の名前が全員違ったことと、ADR や research.md に `claude --help` の英文を写した人がいたためである。

T3 は3人とも同じ1件で check に落ちた。show のために `workspace` に `judged.json` の読み込みを足すと、配列を包むキー `results` が、構造検査の `WRAPPER_KEYS` に登録されていないため NAM-03 で落ちる。登録の表は保護ファイル（`scripts/structure_check.py`）にあり、画面の無いセッションでは hooks の確認に答えられない。3人とも保護ファイルを変えずに手を止め、「`WRAPPER_KEYS` に `results` を1語足す」承認を求めて報告した（agent-3 は、写しで足せば check が全部通ることも確かめていた）。

### エージェントからの提案で入れたこと

T3 の2人が、「方法のモジュール（`recursion` など）も `judged.json` を読めてしまう」と指摘した。harness2 は採点を選択の後だけに動かし、方法から採点の結果へ道が無い。この性質を機械で守るため、[ADR 0008](adr/0008-method-cannot-see-judged.md) を書き、STATE-04 に行を足し、構造検査に方法のモジュールの表（`METHOD_MODULES`）を置いた。方法のモジュールが、名前の中に `judg` がある属性を参照すると落ちる。probe STATE-04-c で効いていることを確かめた。

## レビュー検出率

`.foundation/convergence/review-seeds.json` の16件の違反を、未コミットの変更として置き、「未コミットの変更をレビューして」とだけ頼んだ。違反は、強制に review を含むルールの全部（STR-02、CODE-01、CODE-05、STATE-01、STATE-03、STATE-06、OPS-03、TEST-02、PROC-02、PROC-03、PROC-06、PROC-07、TOOL-04）と、抜け道（TOOL-03 の型無視、DEP-03 の依存の追加、STATE-04 の測定の語の削除）である。機械の検査が拾うのは TOOL-03 の1件だけで、残りの15件はレビューでしか見つからない。

| エージェント | 検出率 | 余計な指摘 | 判定 |
|---|---|---|---|
| review/agent-1 | 1.000（16/16） | CODE-04、OPS-05 | 差し戻し |
| review/agent-2 | 1.000（16/16） | CODE-04、OPS-05、STATE-07 | 差し戻し |
| review/agent-3 | 1.000（16/16） | CODE-04、OPS-05 | 差し戻し |

検出したルールIDの集合は3人で一致した。余計なルールIDは誤りではない。OPS-05 は、seed の `build_select_command` が `claude` のコマンド行を組む3つ目の関数になっていることへの正しい指摘である。CODE-04 は、TOOL-04 の指摘の中で、緩められた上限として名前が出たものである。STATE-07 は、agent-2 の「ルール追加の提案」の節で触れたものである。

## 結論

上限の3ラウンドで止めた。合格基準のうち、次を満たした。

- 最終ラウンドで全エージェントの出力が check を通り、保護ファイルを変えたエージェントはいなかった
- 全課題で files が 1.0（作るファイルの集合が完全に一致）
- T2・T3・ホールドアウト H1 で names が 1.0
- レビュー検出率が全員 100% で、検出したルールIDの集合が一致した
- R1〜R6 の未対処は0件

満たさなかったのは T1 の names（0.559）だけである。原因は1人が ADR の背景に書いた外部の設定キーの名前と、テストの局所変数の名前で、R7（保守性に影響しない違い）と分類した。ADR の本文に書く外部の名前まで決めるルールは、覚えることを増やす割に得るものが小さいので足さなかった。
