# skill-tune-kit 設計の概要

## ゴール

この基盤のゴールは、同じ依頼を受けた別々の作者（人・エージェント）が、同じ書き方をする状態を保つことである。あわせて、変更が局所に収まる構造にすることを目指す。

作るものは、既存の Claude Code スキルを評価データで測りながら改善する道具一式 skill-tune-kit である。利用者は `install.py` で配布物を自分のリポジトリに入れ、配布するスキル `skill-tune` を呼ぶ。スキルは補助 CLI の `status` が示す次の手に従い、4つのサブエージェント（実行役、採点役、学習役、監査役）を起動しながら、計画 → 改善のラウンド → テスト用での最後の評価 → 報告、の順に進める。

## 前提

### 受けた指示

- スキルのブラッシュアップ（精度の改善）をするスキルを作る
- 正解データがある、または作れる場合は、学習用・検証用・テスト用の入力と正解の組を作る
- 正解データが無い場合は、ユーザーとの壁打ちで評価項目を作る
- 独立した学習と独立した検証を回してスキルを改善し、あわせてテスト（評価データ）の正しさを点検し、問題があれば直す。これをループで回す
- 最後にテスト用のデータでテストし、報告する
- 受付で確かめた答え：新しい基盤 skill-tune-kit として作り、対象は任意のスキルにする。候補の採否は検証用のスコアで機械的に決め、人は計画の承認と最後の報告で関わる。データの直しは人の承認を得てから行い、テスト用はループの間は固定して、最後の報告で疑わしい点を示すだけにする

技術の指定は無い。Claude Code のスキルとサブエージェントは、依頼の内容から決まる。

## 全体像

| 技術 | バージョン | 役割 |
|---|---|---|
| Claude Code（スキル、サブエージェント） | 2.1.296 で確認（npm の最新は 2.1.306） | 配布するスキル `skill-tune` と4つのサブエージェント |
| Python | 3.9 以上（3.9.6 で確認） | 補助 CLI `.tune/tune.py`。標準ライブラリだけを使う |
| git | 利用者の環境のもの | 評価の作業場所で、実行役の変更を差分として取り出す |
| uv | 0.11.14 | 開発用の道具を `uvx` で版を固定して呼ぶ |
| ruff | 0.17.1 | 整形と lint |
| mypy | 1.20.2 | 型検査（strict、Python 3.9） |
| unittest | Python の標準ライブラリ | テスト |

補助 CLI は3つの層に分かれる。依存は入口 → 段 → 共有の向きだけで、段どうしは import しない。

- 入口：`tune.py` と `cli`。サブコマンドを段の公開関数に振り分け、画面への出力と終了コードを受け持つ
- 段：`planning`、`status`、`evaluate`、`learn`、`decide`、`audit`、`report`。サブコマンドごとの処理
- 共有：`layout`、`plan`、`contracts`、`workspace`、`fsops`、`proc` などの13のモジュール。パス、型と検証、ファイルの読み書き

進み具合は状態ファイルに書かず、`workspace` が作業場所のファイルの有無とハッシュから求める。`status` はそこから次に実行するコマンドか、起動するサブエージェントを示し、スキルはその行に従うだけで進む。データの流れは [architecture.md](architecture.md) の5章にある。

## ルールを守らせる仕組み

この基盤では、ルールを次の3段で守らせる。

1. **決める**：書き方が分かれうる点ごとに答えを1つ決め、ルールIDを付けて `rules.md` に書いた
2. **縛る**：ルールをできるだけ機械（型、formatter、linter、構造検査、テスト）で強制し、違反例（probe）で効いていることを確かめた。どのルールをどの仕組みで縛っているかは `enforcement-matrix.md` にある
3. **測る**：この基盤を初めて見る独立エージェントに同じ課題を解かせ、書き方の違いを測ってルールを締め込んだ。経過は `convergence-report.md` にある
