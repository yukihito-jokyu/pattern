# 0008 候補の採否は検証用のスコアで機械的に決める

- 状態：採用
- 関係するルール：STATE-03、PROC-07

## 背景

受付で、候補の採否は人ではなく検証用のスコアで機械的に決めると選んでもらった。人が関わるのは、計画の承認、データの直しの採否、最後の適用である。機械で決めるには、採否の規則を1つに決める必要がある。

実行には揺れがあるため、1ケースを複数回（`runs_per_case`）解かせることがある。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 検証用の合格率が上がれば採る | 単純 | 合格率が同じで、検査の通過が増えた改善を採れない。1件を大きく壊しても採る |
| 合格率、同点なら検査の通過率で比べ、退行を禁じる | 部分的な改善も採れる。壊れたケースを見逃さない | 規則が少し増える |

## 決定

次の順で決める。率は整数の件数から分数で計算し、浮動小数の誤差で判定が揺れないようにする。

1. 検証用で、今の版では全実行が合格し、候補では全実行が不合格になったケース（退行）が1件でもあれば、採らない
2. 候補の検証用の合格率が今の版より高ければ、採る
3. 合格率が同じで、候補の検査の通過率が今の版より高ければ、採る
4. それ以外は採らない

- 合格率：ケースごとの「must の検査を全部通った実行の割合」の平均
- 検査の通過率：全実行・全検査のうち、通った検査の割合（should も含む）

学習用の合格率が上がったのに採らなかった場合は、compare.md に「学習用では上がったが検証用で上がらない（合わせすぎの疑い）」と書く。

## 理由

ループを人の応答で止めずに回せる。退行を禁じることで、平均は上がったが大事なケースを壊した候補を採らない。

## 影響

- 採否の規則を変えるときは `metrics.compute_decision` とそのテスト、この ADR を変える
- 今の版の検証用のスコアは、採用した時点の評価を使い続ける。たまたま高く出た候補を採ると、次の候補には不利になる（保守的な側に倒れる）
