# 正解データでケースを作る（reference モード）

入力と正解の組がある、または作れるときの手順である。ケースは「依頼（prompt）＋入力ファイル」と「正解（expected）＋検査」の組で表す。

## 1. 正解データの出どころを決める

AskUserQuestion で、次のどれかを人に選んでもらう。

| 出どころ | 進め方 |
|---|---|
| 人が持っている（過去の依頼と成果物、テストの期待値など） | 場所を聞き、1件ずつケースに取り込む |
| 正解を機械で作れる（変換の規則が決まっている、既存の道具で確かめられる） | 入力を作り、正解は道具か規則で作る。作り方を note に書く |
| 人と一緒に作る | 入力をこちらが作り、正解の案を人に見せて直してもらう |

対象スキルの今の出力を、そのまま正解にしない。今のスキルの誤りが正解に入り、改善を測れなくなる。

## 2. ケースの集め方

- 数：10件以上を勧める。3件未満は check-plan が落とす。10件未満は警告が出る（検証用・テスト用が1〜2件になり、1件の差で採否が動くため）
- 幅：スキルの説明が対象とする入力の種類を、全部1件以上入れる。種類ごとに `group` を付ける。分割はグループごとに割合を保つが、ケースが5件より少ないグループは検証用かテスト用に1件も入らないことがある（割合 0.2 の分割に1件が入る目安が5件）。plan.md の警告に出たグループは、ケースを足すか、`split` で1件を割り当てる
- 難しさ：簡単なもの、境界のもの（空、巨大、表記の揺れ、例外的な形式）、失敗しやすいものを混ぜる
- 独立：同じ入力の言い換えを複数入れない。言い換えが学習用とテスト用に分かれると、テスト用が学習用の暗記で解けてしまう。どうしても入れるなら同じ `group` にし、`split` で同じ分割に固定する

## 3. 検査の選び方

正解との一致は、形が決まっているほど機械の検査で測れる。次の順で選ぶ。

| 正解の形 | 検査 |
|---|---|
| ファイルの中身が1つに決まる | `equals`（`target: file:<パス>`、正解は expected か expected_file） |
| JSON の値が1つに決まる | `json_equals` |
| 返答に必ず出る語・値がある | `contains`、出てはいけない語は `not_contains` |
| 形式（見出し、日付の形など）だけが決まる | `regex` |
| 作ったものを動かして確かめられる | `command`（例 `python3 -m unittest`） |
| 正解と意味が同じかを人の判断で見る | `judge` に `use_expected: true` |

1ケースに `must` の検査を1つ以上置く。`must` は「これを外したら失敗」と言えるものだけにし、望ましいだけのものは `should` にする。

## 4. ファイルの置き方

```text
.tune/targets/<target-id>/dataset/
├── cases.json
└── files/
    └── <ケースの id>/
        ├── input/       実行の前に作業場所の直下へ写る
        └── expected/    expected_file で指す正解のファイル
```

依頼の文の中では、入力ファイルを作業場所からの相対パス（例 `memo.txt`）で書く。

## 5. 確かめること

- `check-plan` が通る
- plan.md の分割の表で、どの分割にも各グループのケースが入っている（警告に「グループ … に1件もありません」が無い）
- 起動回数の見積もりが人の許せる範囲にある（多すぎれば `runs_per_case` か `max_rounds` を下げる）
