# 評価項目を人と決める（criteria モード）

正解が1つに決まらない（文章を書く、設計を提案する、レビューするなど）ときの手順である。ケースは「依頼＋入力ファイル」と「評価項目（judge の検査）」の組で表し、採点役が評価項目ごとに合否を決める。

## 1. 壁打ちで評価項目を決める

AskUserQuestion で、次の順に人と決める。1回の質問は1つの論点にする。

1. 良い出力の条件：対象スキルの SKILL.md と、人が思い浮かべる「良い出力」の例から、条件を5〜10個の案にして見せ、採るものを選んでもらう（multiSelect）
2. 失敗の形：人が過去に困った出力を聞き、それを防ぐ条件を足す
3. 重さ：条件ごとに `must`（外したら失敗）か `should`（望ましい）かを決めてもらう
4. 当てる範囲：全ケースに当てるなら計画の `checks`、特定の種類だけなら `groups` を付けるか、ケースの `checks` に書く

## 2. 評価項目の書き方

採点役が2人いても同じ判定になる1文にする。

| 良い | 悪い（理由） |
|---|---|
| 「返答の最初の段落に、変更の目的が1文で書かれている」 | 「分かりやすい」（人によって判定が分かれる） |
| 「依頼に出てくる関数名を全部、変更点の一覧に挙げている」 | 「網羅的である」（何に対して網羅かが無い） |
| 「推測で補った前提を『前提:』の行に書いている」 | 「前提を適切に扱う」（適切の基準が無い） |

- 1つの評価項目には1つの条件だけを書く。「AかつB」は2つに分ける
- 形で測れる条件（見出しがある、語が含まれる）は judge にせず、`regex` や `contains` にする。機械の検査は採点の揺れが無い
- criteria モードでは、計画の `checks` に `judge` を1つ以上置く

## 3. 入力（依頼）を作る

- 10件以上を勧める。スキルが受ける依頼の種類ごとに `group` を付け、どのグループも2件以上にする
- 実際の利用者の依頼に近い文にする。人に、よくある依頼の例を2〜3件もらい、そこから広げる
- 評価項目が判定できる依頼にする。例えば「前提を書いている」を測るなら、前提が要る依頼を入れる
- `expected` は `null` にする

## 4. 試しに採点してみる

評価項目があいまいかは、採点してみると分かる。ループの最初の評価（v0）の後に監査役が、採点が割れた・根拠が弱い評価項目を `check` の原因として指摘する。指摘を見て、評価項目を直すかを人が決める（直すとゴールが変わるため）。
