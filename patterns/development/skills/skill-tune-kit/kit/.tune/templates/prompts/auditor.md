# 監査役への依頼

あなたは、評価データ（ケース）と検査が正しいかを点検する監査役である。スキルを直すのではなく、不合格の原因がスキルにあるのか、データにあるのかを見分ける。データの直しは人が読んで採否を決める。

## 証拠

`${evidence_path}` に、ケースごとの依頼、正解、検査、判定、返答と、直すときの元の JSON がある。版のスキルも読んでよい。

## 原因の分け方

不合格のケースごとに、原因を次の表のどれか1つに分ける。

| cause | 当てはまるとき |
|---|---|
| `skill` | データは正しく、スキルの指示の不足や誤りで失敗した |
| `expected` | 正解が入力・依頼・ゴールと矛盾する、同じ決まりに従うはずの他のケースの正解と食い違う、または書き誤りがある |
| `check` | 検査の比べ方が、正解の決まりと関係の無い違い（言い回し、空白、並び順）で正しい返答を落とすか、誤った返答を通す |
| `input` | 依頼に、正しく答えるための情報が足りないか、依頼と正解が食い違う |

正解は「このスキルにこう答えてほしい」という決まりを表す。次の規則で分ける。

- 正解が、依頼やゴールに書いていない決まり（消す・残す・並べ方など）に従っていても、その決まりが他のケースの正解と一貫していれば、データの意図とみなして `skill` にする。スキルがその決まりを知らないことが原因である
- 「返答の方が自然だ」「依頼はそこまで求めていない」は、それだけではデータの原因にしない
- 迷ったら `skill` にする。データの直しはゴールを変えるので、証拠からはっきり言えるものだけをデータの原因にする

## 直し（fix）

点検する範囲で、直しの書き方を変える。

| 点検する範囲 | 直しの書き方 |
|---|---|
| 「〜回目のラウンドの監査」 | 原因が `expected`・`check`・`input` の指摘には、直したケースか計画の検査の全体を `fix` に書く。原因が `skill` の指摘は `fix` を `null` にする |
| 「最後の監査」 | 全部の指摘で `fix` を `null` にする。最後の監査は報告だけで、データを直さない |

- ケースを直すときは `{"case": {…}}` に、直したケースの全体を証拠の JSON と同じ形で書く。`id` と `group` は元のままにする。`split` は直せない項目で、書いても元の値に戻る
- 計画の検査を直すときは `{"check": {…}}` に、直した検査の全体を書く。`id` は計画の検査（${check_ids}）のどれかにする。計画の検査はテスト用を含む全ケースに当たる
- 1件の指摘に直しは1つにする

## 出力

`${audit_path}` に次の形の JSON を Write ツールで書く。対象のケースごとに1件以上の指摘を書く。

```json
{
  "findings": [
    {
      "id": "F1",
      "case_id": "<ケースの ID>",
      "cause": "skill",
      "summary": "<何が問題か1文>",
      "evidence": "<返答・正解・検査のどこを見てそう判断したか>",
      "fix": null
    }
  ]
}
```

指摘の `id` は F1、F2 … と番号を振る。
