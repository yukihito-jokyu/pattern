# 学習役への依頼

## 直し方

1. 証拠を全部読み、不合格の原因をケースごとに考える。直すのは、原因がスキルの書き方（手順の抜け、あいまいな指示、誤った例、足りない判断の基準など）にあるものだけにする
2. 正解や検査が誤っていると思う失敗は、スキルを直してまで合わせない。notes に書く
3. 直しは、ケースを超えて通用する一般的な規則にする。ケースの依頼文、正解、固有名詞を候補に写さない。候補に足した20文字以上の行が検証用・テスト用の文と一致すると、候補は落とされる
4. 合格しているケースを壊さない。既存の指示を消す・弱めるときは、合格しているケースの返答がその指示に頼っていないかを確かめる
5. 1ラウンドの変更は、効きそうな少数にする。変更が多いと、どれが効いたか分からなくなる
6. 前のラウンドで不採用になった変更を、そのまま繰り返さない
7. SKILL.md は ${line_limit} 行以内にし、frontmatter の name は変えない。詳細が長くなるときは references/ に分ける

## 出力

候補を直したら、`${proposal_path}` に次の形の JSON を Write ツールで書く。

```json
{
  "changes": [
    {"file": "SKILL.md", "summary": "<何をどう変えたか1文>", "cause": "<直した失敗の原因1文>", "cases": ["<根拠にした学習用のケースの ID>"]}
  ],
  "notes": "<直さなかった失敗とその理由、正解や検査への疑い。無ければ空文字>"
}
```

- `changes` には、変えたファイルを1ファイル1件で全部入れる。変えていないファイルは入れない。`file` は候補のディレクトリからの相対パスにする
- `cases` に書けるのは学習用のケースの ID だけである
- 直すべき点が見つからなければ、候補を変えずに `changes` を空の配列にし、`notes` に理由を書く
