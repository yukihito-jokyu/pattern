# github-actions-kit 収束テストの記録

独立エージェント（この基盤の作成時の会話履歴を持たないセッション）に同じ課題を解かせ、書き方の違い（揺れ）を測った記録である。手順の詳細は、作成に使ったスキルの convergence-test.md にある。各ラウンドの生データは `.foundation/convergence/round-<R>/` にある。

## 条件

| 項目 | 値 |
|---|---|
| 実行方法 | `claude -p`（Claude Code 2.1.308）。基盤のコピーごとに1セッションで、`--permission-mode acceptEdits` と `--allowedTools`（`make`、`gha`、`git diff/status/log`、`ls`、`find`、`grep`、`head`、`tail`、`Skill`）を付けた。コピーの CLAUDE.md・スキル・hooks に加えて、実行したユーザーの `~/.claude/CLAUDE.md` も読み込まれる |
| エージェントの人数 | 3人（課題ごと） |
| 課題 | `.foundation/convergence/tasks.json`（T1-add、T2-change、T3-cross、ホールドアウトの H1-holdout） |
| 合格基準 | 全員の出力が check を通る、files が 1.0、names が 0.8 以上、保護ファイルの変更なし、残った揺れが全部 R7 |

課題の中身は次のとおりである。

| 課題 | 種類 | 依頼の要点 | 測りたいこと |
|---|---|---|---|
| T1-add | add | PR のたびに、キットを空のリポジトリへ導入できるかを CI で確かめる | ci.yml へのジョブの足し方（置き場、ジョブ ID、report の needs） |
| T2-change | change | 処理時間のコメントの表に「失敗したステップ」の列を足す | 変更シナリオ表どおりに `run_report.py` とテストだけで閉じるか |
| T3-cross | cross | Pages のデプロイの前に lint・型検査・テストを通す | 再利用ワークフローを使うか（ステップを写す近道を取らないか）、保守的更新の範囲 |
| H1-holdout | holdout | 毎週 Python 3.14 でテストし、落ちたら Issue を立てる（時刻を書かない） | 定期実行の型と既定値表（ラウンド1・2では使わない） |

### 行った対処のまとめ

- 計測：manifest の `protected` から生成物を外した。課題 T1 の文を直した

最終ラウンドで、違反を仕込んだ未コミットの変更（`.foundation/convergence/review-seeds.json` の11件）を、独立エージェント3人にレビューさせた。プロンプトは「未コミットの変更をレビューして」だけである。

|---|---|---|---|

検出したルールIDの集合は、3人で一致した。種に無いルールIDの中身は次のとおりで、誤った指摘は無かった。

- KIT-06：種が `make docs` を回していないので、`make check` の docs-check が落ちた（機械の検査の結果）
- PROC-07：保守的更新として見ると、再利用ワークフローの入力名の変更が依頼の範囲を超える（正しい指摘）
- STR-02、CODE-03 の一部：種を作った私の誤りで、DEP-04 の種が表に無い `release` トリガーを使い、STR-03 の種の1行目に `rules.md` というファイル名が入っていた。レビュアーは正しく違反と指摘した。種は直したが、直した種でのレビューは回していない
- ERR-02：提案の節で、`with:` の payload に式を埋め込む書き方が ERR-02 の対象外だと指摘した
- TOOL-01、PROC-04、STATE-02：指摘の説明の中でルールに言及しただけ

種の選び方：強制に review を含むルールのうち、PROC-07 と PROC-08 は種にしていない。この2つは依頼文と実装の報告を突き合わせて判定するルールで、未コミットの差分だけを置く種では違反を作れないからである。

レビュアーの提案から、機械の検査の穴が3つ見つかり、その場で直した（probe は 58 件から 61 件になった）。

- ERR-01：決定の文と `err01_shell` が `|| true`・`|| :`・`set +e` を見ていなかった（probe ERR-01-c）
- STR-02：表の目的の行に無いトリガー（`release` など）を `str02_triggers` が見ていなかった（probe STR-02-c）
- CODE-03：1行目のファイル名を `.yml` でしか探していなかった（probe CODE-03-d）。参照実装の setup-kit の1行目にあった `uv.lock` も言い換えた

## 結論

上限の3ラウンドで打ち切った。合格基準は満たしていない。

- 満たしたもの：全員の出力が check を通った（3ラウンド、33セッション）。T1・T2・T3 は files が 1.0 になった。T3 は差分が完全に一致した。レビューの検出率は3人とも 100% で、検出したルールIDの集合も一致した
- 満たさなかったもの：ホールドアウトの H1 で files が 0.333 になり、R2 が3件残った（上の表の #1〜#3）。T1 には R3 が1件残った（#4）。T2 の names はテストのメソッド名のために 0.8 に届かなかったが、これは R7 と分類した

ホールドアウトの揺れは、締め込んだ3つの課題には出てこない命名（定期実行のファイル名、通知のジョブ）と、文書への追記の範囲だった。課題に過剰に合わせたことを示すものではなく、締め込みがまだ届いていない軸だと判断した。
