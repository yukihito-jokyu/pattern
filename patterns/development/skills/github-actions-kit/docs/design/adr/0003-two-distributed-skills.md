# 0003 配布するスキルを gha-workflow と gha-review の2つにし、検査の道具と一緒に写す

- 状態：採用
- 関係するルール：PROC-06、PROC-07、PROC-08、KIT-06

## 背景

依頼の主役は「GitHub Actions を作成・更新するスキル」である。スキルはこのキットの中だけでなく、ワークフローを持つ任意のリポジトリ（配布先）で使われる。スキルだけを配っても、ルールを機械で確かめる道具が配布先に無ければ、作者ごとに書き方が分かれる。

スキルの数と、何を一緒に配るかを決める必要があった。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 作成用・保守的更新用・破壊的更新用の3つのスキル | スキルごとの手順が短い | 「既存を変える」依頼でどのスキルを使うかが揺れる。モードを選ぶ前にスキルを選ぶことになる |
| 実装用1つとレビュー用1つ | 依頼の入口が1つで、モードの選択をスキルの中の決定表（PROC-06）で固定できる | 実装用スキルの中身が長くなる |
| スキルだけを配り、検査は配布先に任せる | 配るものが少ない | 配布先ごとに検査の有無と設定が違い、ルールが守られたかを確かめられない |

## 決定

- スキルは実装用の `gha-workflow`（作成・保守的更新・破壊的更新の3つのモードを持つ）と、レビュー用の `gha-review` の2つにする
- `install.py` が、2つのスキル、`.gha/`（検査の CLI と設定）、`.github/actions/run-report/`、`.github/dependabot.yml` を配布先に写す。`dependabot.yml` は既にあれば残す（収束テストのラウンド1で、導入した直後の `gha check` が PROC-03 で落ちると分かったため足した）
- スキルが読むルールと見本は、`make docs` が正本から作る生成物（`references/rules.md`、`references/examples/`）にする

## 理由

モードの選び方はユーザーの意思で決まり、選び方を間違えると頼まれていない書き換えか、頼んだ改善の不足が起きる。入口を1つにして、モードを決定表で選ばせると、どの作者も同じ手順でモードを決める。レビューは「書いた本人以外が確かめる」役目なので、実装用と分ける。

## 影響

- 配布先では、`uv` と `python3` があれば検査を回せる。GitHub Actions のランナーには両方を入れられる
- キットを上げるときは `install.py` を回し直す。`.gha/zizmor.yml` と `.gha/actionlint.yaml` は配布先ごとに許可表とラベルを変えうるので、`install.py` は既にあれば上書きしない
- スキルの文面に、このキットの開発（KIT 節）だけの手順を混ぜない。KIT 節の手順は AGENTS.md に書く
