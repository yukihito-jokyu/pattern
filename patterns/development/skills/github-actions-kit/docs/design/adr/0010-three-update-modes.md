# 0010 更新を保守的更新と破壊的更新に分け、ユーザーに選んでもらう

- 状態：採用
- 関係するルール：PROC-05、PROC-06、PROC-07、PROC-08

## 背景

依頼には「作成の場合、ユーザーの意図を汲み取る。更新の場合、破壊的更新と既存の書き方や意図を汲み取る更新をユーザーに指定してもらう。破壊的更新の場合、やりたいことを抽出し、その上でベストな書き方をする」とあった。

既存のワークフローを変えるとき、変えてよい範囲は2通りに分かれる。既存の書き方を残して頼まれた所だけを変えるか、既存がしていることを抜き出してルールどおりに書き直すかである。作者が推測で選ぶと、頼まれていない書き換えか、頼んだ改善の不足のどちらかが起きる。また、どちらのモードでも「完了」を機械で判定できる必要がある。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 常にルールどおりに書き直す | 結果が揃う | 既存の意図（コメント、名前、特殊な順序）が消える。頼んでいない変更が混ざる |
| 常に最小限の変更にする | 差分が小さい | 古い書き方のまま残り、破壊的更新の依頼に応えられない |
| 2つのモードを用意し、依頼文の指定で選び、指定が無ければユーザーに聞く | 依頼どおりの範囲で変えられる | モードごとに完了の条件と手順を決める必要がある |

## 決定

モードは作成・保守的更新・破壊的更新の3つにし、PROC-06 の決定表で選ぶ。既存を変える依頼で指定が無ければユーザーに聞き、聞けなければ保守的更新にする。

| モード | 完了の条件 | 機械の支え |
|---|---|---|
| 作成 | `gha check` の指摘0件 | `gha check` |
| 保守的更新 | 指摘を増やさない | `gha check --ratchet HEAD`（(パス, ルールID) ごとの件数を基準の版と比べる） |
| 破壊的更新 | 指摘0件と、棚卸しの全事実の行き先 | `gha intent`（12種類の事実の表）と `gha intent --compare-ref HEAD`（消えた事実） |

## 理由

聞けない状況で保守的更新を既定にするのは、頼まれていない書き換えの方が、改善の不足より取り返しにくいからである。保守的更新で既存の指摘まで0件を求めると、頼まれていない所を直すことになるので、「増やさない」を条件にする。破壊的更新で「やりたいことを抽出する」を作者の読解に任せると粒度が揃わないので、機械で事実を棚卸しし、意図だけを人が埋める。

## 影響

- `gha check --ratchet` は git の履歴を要る。git の無い作業場所では、保守的更新でも `gha check` を回し、既存の指摘を報告に書く
- 棚卸しの事実の種類（`intent.py` の `CATEGORIES`）を増やすときは、PROC-08 と実装用スキルの対応表の書式を一緒に変える
