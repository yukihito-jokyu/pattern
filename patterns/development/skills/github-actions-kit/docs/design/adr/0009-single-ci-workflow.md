# 0009 PR の検証を ci.yml 1つにまとめ、パスの絞り込みをしない

- 状態：採用
- 関係するルール：STR-02、OPS-01

## 背景

PR の検証を、目的ごとのワークフロー（`lint.yml`、`test.yml`、`docs.yml`）に分けるか、1つにまとめるかが作者ごとに分かれる。また、`pull_request` の `paths` で、変更したファイルに関係するワークフローだけを動かす書き方もよく使われる。

`paths` で絞ったワークフローを必須チェックにすると、絞り込みで動かなかった PR はチェックが「待機中」のまま残り、マージできない。これを避ける回避策（同じ名前のダミーのジョブ、パスを判定する外部アクション）は、作者ごとに違う形になる。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 目的ごとにワークフローを分ける | ファイルが短い | 必須チェックの名前が増え、report ジョブも分かれる |
| `paths` で絞る | 関係の無い検査を回さない | 必須チェックと両立しない。回避策が揺れる |
| `ci.yml` 1つにまとめ、絞り込みをしない | 必須チェックを report の1つにできる（[0008](0008-report-job-gates-ci.md)）。どの PR でも同じジョブが動く | 関係の無い検査も回る |

## 決定

PR の検証は全部 `ci.yml` のジョブにする。`pull_request` には絞り込みを書かず、`push` は既定のブランチ1つにする。`pull_request` と `merge_group` を書けるのは `ci.yml` だけにする。

## 理由

必須チェックを1つにすることと、どの PR でも同じジョブが動くことを、検査の時間より優先する。時間は report ジョブで見えるので、遅いジョブはジョブの中身（キャッシュ、並列化）で縮める。

## 影響

- モノレポなどで検査の時間が問題になったら、この ADR を置き換え、ジョブの中で変更を判定する方法を1つに決める。外部アクションに頼らない方法（`git diff` の結果をジョブの出力にする）を第一の候補にする
- `pull_request_target` と `workflow_run` は使わない（DEP-03、OPS-05）
