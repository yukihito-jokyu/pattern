# GitHub Actions のワークフローを作る・直す手順

このスキルは、次の資料と道具を一緒に使う。パスはリポジトリのルートからの相対パスである。

| 資料・道具 | パス | 使い方 |
|---|---|---|
| ルールの全文 | `.claude/skills/gha-workflow/references/rules.md` | `<接頭辞>-<番号>` のルールIDで引く |
| 型ごとの手順 | `.claude/skills/gha-workflow/references/patterns.md` | 1節の振り分け表の番号の節を読む |
| 見本（参照実装の写し） | `.claude/skills/gha-workflow/references/examples/` | 一番近い見本を写して書き始める |
| 検査の CLI（以下 `gha`） | `uv run --locked --script .gha/gha.py <サブコマンド>` | `check`（検査）、`pin`（SHA の解決）、`intent`（棚卸し） |

`.gha/gha.py` が無いリポジトリでは、ワークフローを書かずに、github-actions-kit の `python3 install.py <このリポジトリ>` を先に回すよう報告する。検査の無いまま書くと、ルールを守れたかを確かめられないからである。

既存のファイルと rules.md が食い違ったら、モード（1節）の決まりに従い、食い違いを報告に書く。

## 1. モードを決め、依頼を型に振り分ける

### 1.1 モード（PROC-06）

最初にモードを決める。保守的更新と破壊的更新では、変えてよい範囲がまるで違うからである。

| 状況 | モード |
|---|---|
| 対象のワークフローがまだ無い | 作成 |
| 既存を変える依頼で、「今の書き方は変えずに」「最小限で」「この部分だけ」と指定がある | 保守的更新 |
| 既存を変える依頼で、「作り直して」「全面的に」「ベストな書き方で」と指定がある | 破壊的更新 |
| 既存を変える依頼で、指定が無い | ユーザーに選んでもらう。聞けないなら保守的更新にし、報告の1に書く |

ユーザーに聞くときは、次の文をそのまま使う。

> 既存のワークフローの変え方を選んでください。
> 1. 保守的更新：今の書き方と意図を残し、頼まれた所だけを変えます。既存の古い書き方は直さず、提案として報告します。
> 2. 破壊的更新：今のワークフローがしていることを棚卸ししてお見せし、確かめていただいてから、ルールどおりの書き方で作り直します。

### 1.2 型

| 依頼に含まれること | patterns.md の節 |
|---|---|
| PR の検証、CI、テスト・lint・ビルドを PR で回す、ci.yml にジョブを足す | 1 |
| タグからのリリース、Release の作成、パッケージの公開 | 2 |
| デプロイ、GitHub Pages、クラウドへの反映 | 3 |
| 定期実行、cron、手動で動かす保守（監査、掃除、同期） | 4 |
| 同じステップやジョブを共有する、composite アクション、再利用ワークフロー | 5 |
| PR に各ジョブ・各ステップの処理時間を出す、必須チェックを1つにまとめる | 6 |
| 外部アクションの版を上げる、SHA で固定する、Dependabot | 7 |
| モードが保守的更新 | 8（1〜7 の該当する節と一緒に使う） |
| モードが破壊的更新 | 9（1〜7 の該当する節と一緒に使う） |

- 複数の行に当たる場合は、表の上から順に全部行う
- どの行にも当たらない場合は、実装しない。必要なパターンとルールを提案として報告する。見本に無い形をその場で発明すると、作者ごとに違う形が生まれるからである

## 2. 依頼から決まらない値

推測で決めない。聞ける状況ならユーザーに聞く。聞けない状況なら既定値で決め、報告の3に書く。

| 決めること | 何に響くか | 既定値 |
|---|---|---|
| 既定のブランチの名前 | `ci.yml` の `push.branches`、デプロイの `push.branches` | `git symbolic-ref --short refs/remotes/origin/HEAD` の `origin/` の後ろ。取れなければ `main` |
| ランタイムの版 | setup のアクションの `with:`（CODE-04） | 版のファイル（`.nvmrc`、`.node-version`、`.python-version`、`go.mod`、`.java-version`）。無ければ依存の定義（`package.json`、`pyproject.toml`）を `*-version-file` に書く。どれも無ければ聞く |
| 試す版の組（matrix） | ジョブの数と時間 | matrix を作らない（依頼に「複数の版で」とあるときだけ CODE-02 で作る） |
| ランナーの OS | `runs-on`（NAM-06） | `ubuntu-24.04` |
| 定期実行の時刻 | `schedule`（OPS-04） | 依頼の頻度で、分 `17`、時 `9`、`timezone: Asia/Tokyo`。頻度も無ければ毎週月曜（`17 9 * * 1`） |
| ジョブの時間の上限 | `timeout-minutes`（ASYNC-02） | `10`。長い理由が依頼かリポジトリから分かるときだけ変え、行末に理由を書く |
| 成果物の保存日数 | `retention-days`（STATE-02） | ジョブの間の受け渡しだけなら `1`、人が落として使うなら `7` |
| リリースのタグの形 | `release.yml` の `push.tags` | `v*` |
| environment の名前 | `environment:`（STR-05） | STR-05 の表 |
| 使う secrets と変数の名前 | ステップの `env:`（NAM-05、OPS-02） | 依頼かリポジトリの既存のワークフローにある名前。無ければ聞き、聞けなければ `<サービス>_TOKEN` にして報告の5に書く |
| マージキューを使うか | `ci.yml` の `merge_group` | 使わない（リポジトリの既存の `ci.yml` に `merge_group` があるときだけ書く） |

## 3. 書く前に読む

1. patterns.md の該当する節を最後まで読む
2. rules.md を、モードに応じて読む

   | モード | 読む節 |
   |---|---|
   | 作成 | 用語、STR、DEP、NAM、CODE、ERR、STATE、ASYNC、OPS |
   | 保守的更新 | 上に加えて PROC（特に PROC-02、PROC-07） |
   | 破壊的更新 | 上に加えて PROC（特に PROC-02、PROC-08） |

3. patterns.md の節の「見本」のファイルを `references/examples/` から開き、キーの順、名前、コメントの書き方を確かめる
4. 更新では、対象のファイルを最後まで読み、`.github/` の下で対象を呼んでいるファイル（`uses: ./.github/...` の行）を `grep -rn` で探す

## 4. 作る順序

モードごとに次の順で作る（PROC-01）。各ファイルを保存するたびに `gha check <パス>` を回し、指摘が出たら次に進む前に直す（TOOL-02）。

### 作成

1. 依頼から、目的・トリガー・ジョブ・使う secrets と environment を表にし、2節の値を決める
2. STR-02 の表で、ファイル名と `on:` を決める
3. patterns.md の節の見本を写し、1行目のコメント（CODE-03）、`name`、`on`、`permissions: {}`、`concurrency`（ASYNC-01）、`defaults` を書く
4. ジョブとステップを書く。ジョブ ID は NAM-03、ステップ名は NAM-04、権限は OPS-06 の表で決める
5. `ci.yml` にジョブを足したなら、report ジョブの `needs` に足す（PROC-02）
6. 外部アクションごとに `gha pin <owner/repo>` を回し、出力の `uses:` の行をそのまま写す（DEP-06）。SHA を記憶から書かない
7. `gha check` を回し、指摘を0件にする（PROC-05）

### 保守的更新（PROC-07）

1. 依頼に要る変更の行を決める。それ以外の行（ID、名前、キーの順、コメント、引用の書き方）は1文字も変えない
2. 足す行・変える行だけをルールどおりに書く。外部アクションを足すなら `gha pin` で SHA を得る
3. `gha check --ratchet HEAD <パス>` を回し、増えた組を0件にする。既存の行の違反は直さず、報告の7に提案として書く

### 破壊的更新（PROC-08）

1. `gha intent <パス>` で棚卸しの表を出し、「意図」の列を埋める。依頼文、ファイルの1行目のコメント、ステップの名前から読み取れることを書き、読み取れない行は「不明」と書く
2. 表をユーザーに見せて確かめる。聞けない状況なら、自分の読みで進め、報告の7に「未確認」と書く
3. 作成の手順の2〜6で書き直す。STR-02 でファイル名が変わるなら、新しいファイルを書いてから古いファイルを消す
4. `gha intent <新しいパス> --compare-ref HEAD` を回す。ファイル名が変わったなら `--from <古いパス>` を足す。出た事実を1件ずつ、報告の7の対応表に「移した先」か「落とした理由」で書く
5. `gha check` を回し、指摘を0件にする

## 5. 検証する

次の表の検査を、上から順に全部回す（PROC-05）。

| 状況 | 回す検査 |
|---|---|
| 作成・破壊的更新 | `gha check`（指摘0件） |
| 保守的更新 | `gha check --ratchet HEAD`（増えた組0件） |
| 外部アクションの参照を足した・変えた | 上に加えて `gha pin --verify` |
| このリポジトリに `Makefile` と `docs/design/rules.md` がある（github-actions-kit 自身） | 上に加えて `make docs` と `make check` |

落ちたら、指摘の先頭のルールIDを rules.md で引いて直す。外部ツールの指摘は説明の先頭に `[ツール:規則名]` が付く。次の方法で検査を黙らせない。

- `.gha/` の設定や保護ファイルを変える（TOOL-04）
- 抑止コメントを書く（TOOL-03）
- `continue-on-error` を足す（ERR-01）

どうしても直せない場合は、その状態のまま報告する。許可表に無い外部アクションが要る場合は、`.gha/zizmor.yml` を変えずに、ユーザーに承認を求める（DEP-04）。

## 6. 完了前チェックリスト

該当するファイルを開き、1つずつ確かめる。

- [ ] `ci.yml` のジョブの ID の一覧と、report ジョブの `needs` が一致する（PROC-02）
- [ ] composite アクション・再利用ワークフローの入力を変えたなら、それを呼ぶ全ファイルの `with:` を直した（PROC-02）
- [ ] 新しい secrets・environment を報告の5に書いた（PROC-02）
- [ ] 同じステップの並びが2か所にあれば、composite か再利用ワークフローに切り出した（STR-03）
- [ ] ジョブ ID が NAM-03 の語彙表にある（NAM-03）
- [ ] 1行目は `# <トリガー>で、<成果>`（再利用ワークフローは `# 呼ばれると、<成果>`）で、呼び出し元・ジョブの一覧・ファイル名を書いていない。保守的更新では、トリガーか成果が変わったときだけ書き直した（CODE-03）
- [ ] 1行目のほかのコメントは、版のコメント、時間の上限の理由、コードから読めない理由だけ（CODE-03）
- [ ] ランタイムの版を、版のファイルから読んでいる（CODE-04）
- [ ] クラウドへの認証が OIDC で、長期の鍵を secrets に置いていない（OPS-02）
- [ ] 各ジョブの権限が OPS-06 の表のとおりで、余分な権限が無い（OPS-06）
- [ ] `.gha/` と保護ファイルを変えていない（TOOL-04）
- [ ] 保守的更新なら、差分が依頼に要る行だけ（PROC-07）
- [ ] 破壊的更新なら、`gha intent --compare-ref` の全事実が対応表にある（PROC-08）
- [ ] 5節の検査を全部回し、通った

## 7. 報告する

次の順で書く。

1. モードと、使った型（patterns.md の節の番号）
2. 変えたファイルの一覧（作る順序の順）
3. 2節で決めた値と、その根拠（依頼文、ユーザーの回答、既定値のどれか）
4. 5節の検査の結果（各コマンドの出力の末尾の行）
5. ユーザーが GitHub の画面で設定すること（secrets、environment の保護、ブランチ保護の必須チェックを `report` にすること、Pages の有効化）。無ければ「なし」
6. 「GitHub 上では未実行」の1行（TEST-01）。手元の検査は静的な検査だけだからである
7. モードごとの追記：保守的更新なら既存の行の違反の提案、破壊的更新なら棚卸しの対応表（`| 種類 | 事実 | 扱い |`）
8. 決めきれずに残したこと、ルールと既存のファイルの食い違い
