# GitHub Actions の変更のレビュー手順

指摘は、ルールの全文である `.claude/skills/gha-workflow/references/rules.md` のルールIDに結び付ける。ルールに無いことを理由に差し戻さない。レビュアーごとに基準が変わるのを防ぐためである。以下、`gha` は `uv run --locked --script .gha/gha.py` を指す。

## 1. 対象を決める

- 指定があれば、それを対象にする
- 指定が無ければ、未コミットの変更（`git diff HEAD` と未追跡のファイル）を対象にする
- 未コミットの変更も無ければ、現在のブランチと基準のブランチの差分を対象にする

対象のファイル一覧を、出力の「対象」節に書く。あわせて、変更が作成・保守的更新・破壊的更新のどれかを、依頼文か実装の報告の1から読み取る。分からなければ、既存のファイルの変更は保守的更新として見る。

## 2. 機械の検査を回す

モードに応じて次を回す。落ちたら、出力の要点を「機械の検査」節に載せる。機械が拾った違反を、人手の指摘として重複して書かない。

| モード | 回す検査 |
|---|---|
| 作成・破壊的更新 | `gha check` |
| 保守的更新 | `gha check --ratchet <基準の版>` |
| `uses:` の行が変わった | 上に加えて `gha pin --verify` |
| リポジトリに `Makefile` と `docs/design/rules.md` がある（github-actions-kit 自身） | 上に加えて `make check` |

## 3. 抜け道を確かめる

| ルールID | 確認 | 見るもの |
|---|---|---|
| TOOL-04 | 保護ファイルの変更 | `.gha/` の下のファイル（検査の設定、`gha.py`、ロックファイル）が差分にあるか。github-actions-kit 自身では `.foundation/manifest.json` の `protected` に当たるファイルも見る |
| TOOL-03 | 抑止コメント | `# zizmor: ignore`、`# yamllint disable`、`# shellcheck disable` などが差分にあるか |
| ERR-01 | 失敗の握りつぶし | `continue-on-error`、`|| true`、`set +e` が差分にあるか |
| DEP-04 | 外部アクションの追加 | `.gha/zizmor.yml` の `allow` に無い `uses:` が差分にあるか。あれば、ユーザーの承認が報告にあるか |

## 4. 機械で拾えないルールを確かめる

rules.md で強制に `review` を含むルールは、3節かこの表の1列目に全部載っている。差分に関係する行を確かめる。

| ルールID | 確認方法 | 違反の典型例 |
|---|---|---|
| STR-03 | 差分の中と `.github/` の既存のファイルで、同じステップの並び（`uses`・`with`・`run` が同じ2ステップ以上）が2か所以上にあるか | 3つのジョブに `Set up uv` と `Install dependencies` を同じ形でコピーした |
| NAM-03 | 各ジョブのステップの中身から役割を読み、ジョブ ID が NAM-03 の表の語と合っているか | テストを回すジョブの ID が `ci` や `run-tests` |
| CODE-03 | 1行目が成果だけか（途中の手順・ジョブの一覧を書いていないか）。保守的更新で1行目が変わったなら、トリガーか成果が変わったか。1行目のほかのコメントが、版のコメント・時間の上限の理由・コードから読めない理由のどれかか | `# チェックアウトする` のように、次の行がすることを書いている。前段に検査を足しただけで1行目に「検査を回してから」と足した |
| CODE-04 | setup のアクションの `*-version:` に版を直接書いていないか。リポジトリに `.nvmrc`・`.python-version`・`go.mod` などがあるか | `.nvmrc` があるのに `node-version: "22"` と書いた |
| OPS-02 | クラウドへの認証に長期の鍵（`AWS_ACCESS_KEY_ID` など）を使っていないか。OIDC の公式のアクションで置き換えられるか | `secrets.AWS_SECRET_ACCESS_KEY` を `env:` に渡している |
| OPS-06 | 各ジョブの `permissions` を、OPS-06 の表と、ジョブがしていること（checkout、コメント、Release、OIDC）に照らし、余分な権限が無いか | Release を作らないジョブに `contents: write` を付けた |
| PROC-02 | 5節の表の組がそろっているか | 5節を見る |
| PROC-07 | 保守的更新なら、差分が依頼に要る行だけで、既存の行の名前・順・コメント・引用が変わっていないか | ジョブを1つ足す依頼で、既存の全ステップの `name` を書き換えた |
| PROC-08 | 破壊的更新なら、`gha intent <新しいパス> --compare-ref <基準の版>`（名前が変わったら `--from <古いパス>`）の全行が、報告の対応表にあるか | 古いワークフローの Slack 通知が消え、対応表にも無い |

## 5. ファイルをまたぐ対応を確かめる

PROC-02 の表の各組について、両側のファイルを開いて突き合わせる。

| 変更 | 開くファイル | 突き合わせること |
|---|---|---|
| `ci.yml` のジョブを足す・消す・名前を変える | `ci.yml` の `jobs` と report の `needs` | report 以外の全ジョブ ID と `needs` の要素が一致する |
| 外部アクションを新しく使う | `uses:` の行と `.gha/zizmor.yml` の `allow` | `allow` にあるか、承認が報告にある |
| composite アクション・再利用ワークフローの入力を変える | 定義の `inputs` と、呼ぶ全ファイルの `with:`（`grep -rn "uses: ./.github/"` で探す） | 必須の入力が全部渡され、無い入力を渡していない |
| 再利用ワークフローの出力を変える | 定義の `outputs` と、`needs.<ジョブ>.outputs.<名前>` を読む行 | 読む名前が全部定義にある |
| 新しい secrets・environment を使う | 差分と実装の報告の5 | 名前が全部報告にある |

## 6. 出力の形式

必ず次の形で出す。

```
# レビュー結果

## 判定
承認 または 差し戻し

## 対象
- <ファイルの一覧>
- モード：<作成・保守的更新・破壊的更新>

## 機械の検査
<2節の各コマンドの結果。通った、または落ちた（要点）>

## 指摘
| # | ルールID | 場所 | 根拠（実際の記述） | 直し方 |
|---|---|---|---|---|
| 1 | <ID> | <パス>:<行> | `<該当の記述>` | <直し方> |

指摘が無ければ「なし」と書く。

## ルール追加の提案
<ルールには無いが、揺れや問題になりうる点。指摘とは分けて書く。無ければ「なし」>
```

- 判定は機械的に決める。2節の検査が通り、かつ指摘が0件なら「承認」、それ以外は「差し戻し」
- 指摘は場所の順に並べる
- 同じ違反が複数の箇所にあれば、箇所ごとに1行ずつ書く
