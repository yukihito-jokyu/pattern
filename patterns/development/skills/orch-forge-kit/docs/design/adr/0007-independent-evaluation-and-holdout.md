# 0007 評価の独立性を保ち、ホールドアウトと写しの検査で評価課題への過剰な適合を防ぐ

- 状態：採用
- 関係するルール：STATE-01、STATE-02、OPS-04、PROC-07

## 背景

設計役・構築役・分析役は対象スキルを書き、同じ評価課題で測る。このとき、スキルが評価課題に合わせた答え（課題文の写し、課題だけで効く手がかり）を持つようになりうる。そうなると、評価課題の指標は上がっても、実際の依頼では良くならない。また、評価の実行が元のリポジトリを書き換えたり、前の実行の結果が次の実行に漏れたりすると、測った値が信用できない。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 評価課題だけで測る | 課題が少なくて済む | 過剰な適合を見つけられない |
| ホールドアウトを最後の評価だけで使い、設計役・構築役・分析役に見せない。バンドルに評価課題の文の写しがあれば落とす | 過剰な適合を、最後の評価の差と検査で見つけられる | 課題を余分に作る必要がある |

## 決定

- 評価課題のうち ID が `H` で始まるものをホールドアウトにし、最後の評価だけで使う。設計役・構築役・分析役に渡す charter（visible-charter.md）からは除く
- `bundle-check` と `propose` は、バンドルに評価課題の文（`prompt` と `acceptance`）が20字以上そのまま現れたら落とす（バンドルの決まり。`bundle.RULES`）
- 実行ごとにリポジトリを写し、git の基準のコミットからの差分で事実を集める
- 報告で、最後の評価の課題とホールドアウトの値が大きく違えば、人に判断してほしいこととして挙げる

## 理由

ホールドアウトは、学習でいう検証用のデータと同じ役割を持つ。スキルを書く役が見られない課題で同じ水準が出れば、改善は一般化していると判断できる。写しの検査は、最も単純な過剰な適合を機械で止める。

## 影響

- forge-goals では、ホールドアウトの課題を1件以上作る手間がかかる
- 20字に満たない写しや、言い換えた写しは検査をすり抜ける。最後の評価の差と、人の採否で補う
- サブエージェントは元のリポジトリの `.forge/targets/<id>/charter.json` を読めてしまう。プロンプトで読むファイルを示し、charter.json を読まないよう書く
