# orch-forge-kit 設計の概要

## ゴール

この基盤のゴールは2つある。

1. **作るもの**：任意のリポジトリに、開発用のオーケストレーションスキル（メインのセッションで動き、Agent ツールで役ごとのサブエージェントを起動して実装・確認・報告を進めるスキル。以下、対象スキル）を作り、人と一緒に決めたゴールと評価指標に向けて良くしていく道具一式を配る
2. **作り方**：この道具を変える別々の作者（人・エージェント）が、同じ書き方をする状態を保ち、変更が局所に収まる構造にする

1つ目の道具は、次の流れで動く。

1. **決める**（forge-goals）：人と対話して、対象スキルの目的、ゴール、指標と閾値、評価課題と受け入れ条件、実行の条件、予算を決め、`charter.json` にまとめて承認を記録する
2. **作る**（forge-build）：対象スキルがまだ無ければ、設計役のサブエージェントが役と手順を設計し、人が承認した設計から、構築役のサブエージェントが下書きを書く。補助 CLI がバンドルの決まりで検査し、人が入れると決めたら対象のリポジトリの `.claude/` に入れる
3. **測る**（forge-run）：補助 CLI が、評価用のコピーの中で実行役（`claude -p`）を起動し、対象スキルに評価課題を解かせる。実行の記録から、起動したサブエージェント・編集した主体・費用・時間を数え、採点役のサブエージェントが受け入れ条件と手順を判定し、補助 CLI が指標を計算する
4. **直す**（forge-run）：must の指標が足りなければ、分析役のサブエージェントが原因を分類してスキルの写しを直し、同じ課題で候補を測って比べる。採るかは人が決める
5. **確かめる**（forge-run）：最後に、設計役・構築役・分析役に見せなかったホールドアウトの課題も含めて測り、報告を書く

## 前提

### 受けた指示

- 「開発用のオーケストレーションスキルを、サブエージェントを使って構築し、より良いものにするスキルをパターンとして作って」
- 「作成する実装用のオーケストレーションスキルのゴールや評価指標は人間と一緒に考えるようにする」

受付で、次の4点をユーザーに選んでもらった。

| 項目 | 選んだもの |
|---|---|
| 既存の基盤との関係 | 新しい独立した基盤（skill-brushup-kit の教訓は引き継ぐが、コードは共有しない） |
| オーケストレーションの形 | Agent ツールで、役ごとのサブエージェントの定義（`.claude/agents/`）を起動する |
| 評価の実行役 | 補助 CLI が `claude -p` を起動する（[ADR 0002](adr/0002-roles-and-claude-p-executor.md)） |
| 名前 | orch-forge-kit、配るスキルは `forge-goals`・`forge-build`・`forge-run` の3つ（[ADR 0004](adr/0004-three-human-invoked-skills.md)） |

### 既定値で決めた事項

| 事項 | 決めたこと | 記録 |
|---|---|---|
| 補助 CLI の言語と依存 | Python 3.9 の標準ライブラリだけ | DEP-03、[ADR 0005](adr/0005-mypy-1-20-for-python-3-9.md) |
| サブエージェントの分け方 | 設計役・構築役・採点役・分析役の4つ | [ADR 0002](adr/0002-roles-and-claude-p-executor.md) |
| 配布物と評価用のコピーの置き場 | 配布物の正本は `kit/claude/`、評価用のコピーは OS の一時ディレクトリ | [ADR 0003](adr/0003-copies-outside-repository.md) |
| 権限 | サブエージェントと実行役の権限を広げない | OPS-05、[ADR 0006](adr/0006-no-permission-widening.md) |
| 過剰な適合の防ぎ方 | ホールドアウトと、評価課題の文の写しの検査 | [ADR 0007](adr/0007-independent-evaluation-and-holdout.md) |
| 生成するスキルの形 | 決まりを `bundle.RULES` の表に固定する | STR-06、[ADR 0008](adr/0008-fixed-bundle-shape.md) |
| 委任や費用の測り方 | 実行の記録（stream-json）の、文書にある項目だけから数える | [ADR 0009](adr/0009-measure-from-documented-stream-fields.md) |

| 生成するスキルの検索の書き方 | Glob・Grep を前提にせず、Bash の `find`・`grep` で探すと書かせる | [ADR 0012](adr/0012-no-glob-grep-with-bash.md) |

## 全体像

| 技術 | バージョン | 役割 |
|---|---|---|
| Claude Code（スキル、サブエージェント、`claude -p`） | 2.1.296 で確認（npm の最新は 2.1.304） | 配布するスキル3つとサブエージェント4つが動く場所。評価の実行役 |
| Python | 3.9.6 | 補助 CLI、構造検査、テスト |
| git | 2.50.1 で確認 | 評価用のコピーの差分を取る |
| uv | 0.11.14 | ruff と mypy を版を固定して呼ぶ |
| ruff | 0.17.1 | 整形と lint |
| mypy | 1.20.2 | 型検査（Python 3.9 を対象） |
| unittest | 3.9.6 の標準ライブラリ | テスト |

補助 CLI は、2つ以上の段が使う「共有のモジュール」と、1つの段を受け持つ「段のモジュール」に分かれる。段のモジュールは共有のモジュールだけに依存し、段どうしは依存しない。どの段にいるかはファイルの有無から `status` が決め、スキルは `status` の指示に従ってコマンドを実行し、サブエージェントを起動し、人に聞く。詳しくは [architecture.md](architecture.md) にある。

## ルールを守らせる仕組み

この基盤では、ルールを次の3段で守らせる。

1. **決める**：書き方が分かれうる点ごとに答えを1つ決め、ルールIDを付けて `rules.md` に書いた
2. **縛る**：ルールをできるだけ機械（型、formatter、linter、構造検査、テスト）で強制し、違反例（probe）で効いていることを確かめた。どのルールをどの仕組みで縛っているかは `enforcement-matrix.md` にある
3. **測る**：この基盤を初めて見る独立エージェントに同じ課題を解かせ、書き方の違いを測ってルールを締め込んだ。経過は `convergence-report.md` に、締め込みで足した・直したルールの決定は [ADR 0010](adr/0010-convergence-rules.md) にある。配布物が実際に動くことは、見本のリポジトリでの通しの実行で確かめた（`convergence-report.md` の同じ名前の節）
