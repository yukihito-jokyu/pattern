# orch-forge-kit 収束テストの記録

独立エージェント（この基盤の作成時の会話履歴を持たないセッション）に同じ課題を解かせ、書き方の違い（揺れ）を測った記録である。手順の詳細は、作成に使ったスキルの convergence-test.md にある。各ラウンドの生データは `.foundation/convergence/round-<R>/` にある。

## 条件

| 項目 | 値 |
|---|---|
| 実行方法 | `claude -p`（Claude Code 2.1.296）。`--permission-mode acceptEdits`、`--no-session-persistence`、`--allowedTools` で `Skill` と `make`・`python3`・`git diff` などの Bash を許可（`.foundation/manifest.json` の `convergence.runner`）。各セッションは基盤のコピーの中で動き、`.foundation/convergence/` とこの記録は写さない。ユーザー単位の設定（`~/.claude/CLAUDE.md`）も読み込まれる |
| エージェントの人数 | 3人（課題ごと） |
| 課題 | `.foundation/convergence/tasks.json`（T1-add：指標の追加、T2-change：構築役のプロンプトへの値の追加、T3-cross：設計の承認に人のメモを足し、構築役まで通す、H1-holdout：charter と実行役の引数への項目の追加） |
| 合格基準 | 全出力が `make check` を通る、全課題で `files` が 1.0、`names` が 0.8 以上、R1〜R6 の未対処が0件、ホールドアウトでも同じ、レビュー検出率が全エージェントで 100% |

## 収束テストの前に直したこと

収束テストを始める前に、ルールと見本（参照実装）の食い違いを2つ見つけて直した。見本がルールに違反していると、エージェントが見本を真似るかルールに従うかで割れるからである。

| ルール | 食い違い | 対処 |
|---|---|---|
| NAM-02 | 語彙表に無い動詞（`copy_tree`、`launch`、`recommend` ほか）で始まる関数が見本に多くあり、`cli.build_parser` は表の `make_` と同じ意味の別名だった | 決定を「表の意味の関数は表の動詞で始め、同じ意味の別名を使わない」に絞った。別名（`get_` ほか）は構造検査 `check_names` と probe NAM-02-a で落とす。`build_parser` を `make_parser` に直した |
| CODE-01 | 「引数の list を変えない」と決めていたが、見本の検証の関数は呼び出し側の `problems` に問題を足していく形だった | `problems` を例外として明記した |

## 見本のリポジトリでの通しの実行

収束テストは、この基盤を変える作者が同じものを書くかを測る。これとは別に、配る道具そのもの（補助 CLI、スキル3つ、サブエージェント4つ）が、対象のリポジトリで最後まで動くかを確かめた。

### 条件

| 項目 | 値 |
|---|---|
| 対象のリポジトリ | 一時ディレクトリに作った在庫のライブラリ（`inventory/`、検査の `check.py`、`AGENTS.md`、`README.md`、git） |
| 入れ方 | `python3 install.py --dest <リポジトリ>` |
| charter | forge-goals は人との対話が中心なので、通しの実行では人の役を作成者が受け持ち、`charter-new` → 記入 → `charter-check` → `charter-approve` を CLI で行った |
| スキルの起動 | `claude -p "/forge-build <target>"` と `claude -p "/forge-run <target>"`。`--permission-mode acceptEdits`、`--allowedTools "Bash(python3 .forge/forge.py *)"`。人に聞く場面の答え（評価の開始は「始める」、採否は推奨どおり）を `--append-system-prompt` で渡した |

### 1回目：既定の charter（must の指標 5つ、should の指標 2つ）

| 段 | 結果 | 費用 |
|---|---|---|
| forge-build | 設計役が役2つ（実装役・レビュー役）と手順 S1〜S6 を設計し、構築役が SKILL.md、references 3つ、サブエージェント2つを書いた。`bundle-check` が通り、`install` で入った | $2.38（584 秒） |
| forge-run（最初の評価） | 実行役 2回。どちらも2つのサブエージェントを起動し、must の指標を全部満たしたので、改善のラウンドは行わなかった | 実行役 1回 $0.75〜$0.77 |
| forge-run（最後の評価） | ホールドアウトを含めて実行役 4回。ホールドアウトでは flow_conformance（should）が 0.917 で未達、ほかは全部達成。報告を書いた | 実行役 1回 $0.71〜$0.79 |

forge-run のメインのセッションは、権限の問題で2回止まり、3回目に最後まで進んだ（3回の合計 $2.79）。見つかった問題と対処は次のとおりである。

| # | 見つかったこと | 対処 |
|---|---|---|
| 1 | スキルの `allowed-tools` は、スキルを呼んだターンの間だけ効く。`execute` の完了の通知で始まるターンでは、`status` と `collect` が承認待ちで拒まれた | `install.py` が `.claude/settings.json` の `permissions.allow` に同じルールを足す（[ADR 0011](adr/0011-install-cli-permission-rule.md)） |
| 2 | 信頼の確認を済ませていないワークスペースでは、`.claude/settings.json` の `permissions.allow` が無視される | README と ADR 0011 に、一度画面で開いて信頼の確認に答えること、`claude -p` では `--allowedTools` を渡すことを書いた |
| 3 | 報告が、採った変更が無いのに「課題への過剰適合の疑いがある」と書いた | `report.py` が、採ったラウンドがあるときだけこの文を書き、無いときは「課題の違いか実行の揺れ」と書くように直し、`tests/test_report.py` に確かめる assert を足した |

### 2回目：must の独自の指標を足した charter

1回目は最初の評価で must を全部満たし、改善のラウンドが動かなかった。そこで、同じスキルを対象に、別の作業領域（`stock-orch-strict`）の charter に must の独自の指標 `custom_1`（「最後の返答の1行目が『結果: 完了』か『結果: 未完了』のどちらかだけの行で、その後に報告の項目が続く」）を足して、もう1回 `/forge-run` を回した。今のスキルは報告を見出しで始めるので、最初の評価では満たさないはずの条件である。

| 段 | 結果 | 実行役の費用 |
|---|---|---|
| 最初の評価 | custom_1 が 0.000（2回とも未達）。ほかの must は達成 | 1回 $0.72〜$0.75 |
| 分析と候補 | 分析役が、報告の1行目の決まりを SKILL.md の `## 報告`・手順 S6・`## してはいけないこと` と closing-format.md に足す変更を1つ提案した。`propose` の検査が通り、候補を同じ課題で測った | 1回 $0.72〜$0.75 |
| 比べる・決める | custom_1 が 0.000 → 1.000。should の flow_conformance は 1.000 → 0.833 に下がった。補助 CLI の推奨は「採用」で、推奨どおり採用し、今のバンドルを `rounds/round-1/previous/` に退避して置き換えた | — |
| 最後の評価 | ホールドアウトを含めて custom_1 は 1.000、must は全部達成。flow_conformance は 0.917 | 1回 $0.68〜$0.76 |

メインのセッションは1回で最後まで進み（$3.76、権限で拒まれた操作は0件）、`decide` が `.claude/` のスキルを置き換えた。2回の通しの実行で、forge-build と forge-run の全部の段（設計、構築、入れる、評価、分析、提案、候補、比べる、決める、最後の評価、報告）が動いた。

分析役は、flow_conformance が下がった原因を、スキルの不具合ではなく評価の側の所見（S6）として報告に書いた。その中に、配る道具の不具合が1つあった。

| # | 見つかったこと | 対処 |
|---|---|---|
| 4 | 構築役が書いたスキルは、メインのセッションの手順で「Glob で一覧する」と書いていた。しかし macOS・Linux の Claude Code は、Bash のあるセッションに Glob・Grep を入れない（実行役の init の `tools` にも無かった）。実行役は `ls` などで代わりに探し、スキルの「Bash で検査のほかを実行しない」に反した。人が画面で使うときも同じことが起きる | バンドルの決まり B13 を足し、スキルのファイルに Glob・Grep を書かせず、Bash を持つサブエージェントに Glob・Grep を持たせないようにした。設計の検査でも同じ組み合わせを落とす（[ADR 0012](adr/0012-no-glob-grep-with-bash.md)） |
