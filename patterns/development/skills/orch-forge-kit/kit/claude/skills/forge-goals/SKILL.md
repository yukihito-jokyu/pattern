# forge-goals

オーケストレーションスキルを「作る」「良くする」には、先に「良い」の中身を決める必要がある。中身が決まっていないと、設計の案や改善の案を出しても、採るか捨てるかを判断できないからである。このスキルでは、その中身を人と一緒に決め、`charter`（目標の取り決め）という1つのファイルにまとめる。

charter に書くものと、誰が決めるかは次のとおりである。

| 項目 | 中身 | 決め方 |
|---|---|---|
| 目的・ゴール | このスキルで何ができるようになってほしいか | 人の言葉をそのまま書く。あなたは問いかけるだけにする |
| 指標と閾値 | ゴールに届いたかを測る数と、合格の線。`must`（必ず満たす）か `should`（満たしたい） | 人が選ぶ。あなたは案を出す |
| 評価課題 | スキルを試す依頼と、その受け入れ条件 | 人の言葉をそのまま書く。あなたは書き方の決まりを伝える |
| 環境 | 検査のコマンド、変えてはいけないファイル | 人が選ぶ。あなたはリポジトリから読み取った案を出す |
| 実行の条件と予算 | 評価でスキルを動かす `claude -p` の条件、1課題あたりの実行の回数、改善のラウンドの上限 | 人が選ぶ。あなたは案を出す |

charter は人の承認を記録してから使う。承認の後に1文字でも変えると、評価は止まる（承認し直しが要る）。

## 役割

このスキルはメインのセッションだけで進め、サブエージェントを起動しない。人と対話して決めた値を charter.json に書き、補助 CLI（`python3 .forge/forge.py`）で検査と承認の記録を行う。

## 手順

1. `python3 .forge/forge.py targets` を実行する。失敗した（`.forge/forge.py` が無い）ときは、orch-forge-kit の `install.py` で入れるよう人に伝えて終える
2. 対象のスキル名を決める。引数で渡されていればそれを使う。無ければ、手順1の表を見せ、既にあるスキルを直すか、新しいスキルを作るかを AskUserQuestion で聞き、新しく作るなら名前（kebab-case、`forge-` で始めない）を聞く。`target.id` はスキル名と同じにする。作業領域の対象の一覧に同じ id があれば、手順10へ進み、検査と見直しから始める
3. 目的を聞く。「このスキルで、どんな依頼を、どうこなせるようになってほしいか」を文章で聞き、返ってきた文をそのまま `purpose` にする。既にあるスキルなら、先に SKILL.md と、そこから参照されるファイルを読み、手順を5行以内に要約して見せてから聞く
4. ゴールを聞く。「何ができたら成功か」を、2〜4個、1文ずつ文章で書いてもらう。返ってきた文をそのまま `statement` にし、順に `G1`、`G2` と番号を振る。文に測れない言葉（きれいに、適切に）があれば、何を見れば満たしたと言えるかを聞き返し、人に書き直してもらう
5. 指標と閾値を決める。`python3 .forge/forge.py metric-catalog` で一覧を出し、ゴールごとに指標を1つ以上結び付けた案を作る。指標の意味は [references/metric-catalog.md](references/metric-catalog.md) にある。案を表（id、名前、閾値、must/should、結び付くゴール）で見せ、AskUserQuestion で確かめる
6. 評価課題を決める。書き方の決まりと例は [references/eval-set-guide.md](references/eval-set-guide.md) にあるので、先に読み、決まりを人に伝える。課題の依頼文（`prompt`）と受け入れ条件（`acceptance`）は、1件ずつ人に文章で書いてもらい、そのまま使う。評価と改善に使う `T<番号>` を2〜4件、最後の評価だけで使うホールドアウト `H<番号>` を1〜2件にする
7. 環境を決める。リポジトリから下の表の値を読み取って案を作り、AskUserQuestion で確かめる
8. 実行の条件と予算を決める。下の表の既定を案にし、AskUserQuestion で確かめる
9. charter を書く。charter が無ければ `python3 .forge/forge.py charter-new --target <id> --skill-name <スキル名>` でひな形を作り、手順3〜8で決めた値を `.forge/targets/<id>/charter.json` に書く。項目の形は [references/charter-schema.md](references/charter-schema.md) にある
10. `python3 .forge/forge.py charter-check --target <id>` を実行する。問題が出たら直し、出なくなるまで繰り返す。直すのが人の言葉の値（目的、ゴール、評価課題）なら、問題を見せて人に書き直してもらう
11. 承認を聞く。`.forge/targets/<id>/charter.md`（人が読む版）の要点と、charter-check の出力の「実行役の起動（上限）」と「費用の上限の見積もり」を見せ、AskUserQuestion で「承認する／直したい」を聞く。承認なら `python3 .forge/forge.py charter-approve --target <id>` を実行する。直したいなら、該当する手順へ戻る
12. 次の段を伝える。対象のスキルがまだ無ければ `/forge-build <id>` で作ることを、既にあれば `/forge-run <id>` で評価と改善を始めることを伝える

### 環境（手順7）

| 項目 | 読み取る場所 | 決まり |
|---|---|---|
| `check_command` | `Makefile`、`package.json` の scripts、CI の設定 | `check_pass` を使うなら必須。評価用のコピーの中で、リポジトリのルートから実行される |
| `protected_paths` | lint・型・テストの設定、CI、ルールの文書 | glob で書く。`*` は `/` をまたぐ。`protected_untouched` を使うなら1件以上 |
| `skip_dirs` | 大きな生成物・キャッシュ | コピーから除く名前。`/` で始めるとルート直下だけ |
| `link_dirs` | `node_modules` などの依存 | コピーせず元へのリンクにする名前 |

検査コマンドが `.forge/` の下を見ないことも確かめる。見てしまう場合は、検査の除外設定に `.forge/` を足すよう人に伝える。

### 実行の条件と予算（手順8）

評価では、評価用のコピーの中で `claude -p` を起動し、対象のスキルを評価課題で使わせる。この起動を実行役と呼ぶ。実行役は人に質問できず、許していない操作は確認なしで拒否される。

| 項目 | 既定 | 決まり |
|---|---|---|
| `executor.allowed_tools` | 空 | ファイルの編集は許してある。スキルが回すコマンド（検査など）を `Bash(make check)` の形で足す。足りないと、実行役の操作が拒否され、採点の所見に「拒否された操作」が出る |
| `executor.model` | 空（Claude Code の既定） | モデルを固定するときだけ書く |
| `executor.max_budget_usd` | 3.0 | 1回の実行の費用の上限（ドル） |
| `executor.timeout_sec` | 1800 | 1回の実行の時間の上限（秒） |
| `executor.parallel` | 3 | 同時に動かす実行役の数 |
| `budget.agents` | 3 | 1課題あたりの実行の回数。一致度の指標を使うなら2以上 |
| `budget.max_rounds` | 3 | 改善のラウンドの上限 |

## 人に確かめること

各手順で人に聞くときは、値の種類で聞き方を分ける。

| 値の種類 | 聞き方 |
|---|---|
| 選ぶ値（対象、指標、閾値、must/should、環境、実行の条件、予算、承認） | AskUserQuestion を使う。1回の呼び出しで聞くのは4問まで、選択肢は1問に2〜4個で、「その他」は自動で付く。あなたの案を先頭の選択肢にし、名前の末尾に `（推奨）` を付ける |
| 人の言葉を残す値（`purpose`、ゴールの `statement`、評価課題の `prompt` と `acceptance`） | AskUserQuestion を使わずに文章で聞き、返ってきた文をそのまま使う。あなたの案で埋めない。書き方の決まりと例は伝えてよい |

- 人が答えられないとき（返事が無い）は、charter を書かずに止まる。承認の無い charter では、forge-build と forge-run は進まない

## 報告

最後の返答に、次の項目をこの順で書く。

1. 対象（`target.id` とスキル名、作るか直すか）
2. ゴールと、結び付けた指標（表）
3. 評価課題の件数（T と H）
4. 実行役の起動（上限）と費用の上限の見積もり
5. 承認の状態と、次に呼ぶスキル（`/forge-build <id>` か `/forge-run <id>`）

## してはいけないこと

- 人の答えを待たずに charter-approve を実行すること。charter は人と合意したことの記録だからである
- `approval` の項目を手で書くこと。承認は charter-approve だけが書く
- 目的・ゴール・評価課題を、あなたの案で埋めること。人のゴールではなく、あなたのゴールが評価の基準になる
- 評価課題に、対象スキルの文章をそのまま写すこと。スキルに書いてあることを確かめるだけの課題になり、改善の余地を測れない
- 対象のスキルを、このスキルの中で作ったり直したりすること。作るのは forge-build、直すのは forge-run の役目である
