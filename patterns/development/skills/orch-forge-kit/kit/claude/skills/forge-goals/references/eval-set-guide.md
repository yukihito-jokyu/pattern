# 評価課題の書き方

評価課題は、対象のスキルを試す依頼である。評価では、評価用のリポジトリのコピーの中で `claude -p` を起動し、`/<スキル名> <課題の依頼文>` を渡す。実行役は人に質問できないので、依頼文だけで作業が決まる必要がある。

課題の良し悪しで、改善の向きが決まる。分析役は、評価で足りなかった指標の原因をスキルの書き方に求めて直すため、課題がスキルの弱い所を突いていないと、直す所が見つからない。

## 目次

- 依頼文の決まり
- 受け入れ条件の決まり
- 課題の組み方
- ホールドアウト
- 良い例と悪い例

## 依頼文の決まり

| 決まり | 理由 |
|---|---|
| 人が実際に `/<スキル名>` の後に書く形で書く | 評価は、実際の使い方での振る舞いを測るためにある |
| 1つの課題は1つの依頼にし、1回の実行の時間の上限（`executor.timeout_sec`）に収まる大きさにする | 打ち切られた実行は、全部の判定項目が未達になる |
| 答え（作るファイル名、関数名、手順）を書かない | 答えを書くと、スキルの手順ではなく依頼文が結果を決め、スキルの差を測れない |
| スキルの文章を写さない | スキルに書いてあることを確かめるだけの課題になる |

## 受け入れ条件の決まり

- 採点役が、変更の差分と最後の返答だけで「満たした / 満たしていない」を判定できる1文にする
- 振る舞い（何を渡すと何が起きるか）か、成果物（テストがある、文書に書いてある）で書く
- 1つの条件に1つの事柄だけを書く。「AかつB」は2つに分ける

## 課題の組み方

オーケストレーションスキルの弱い所は、次の場面で出やすい。課題の中に、少なくとも1つずつ入れる。

| 場面 | 例 | 主に動く指標 |
|---|---|---|
| 作業をサブエージェントに分けるかどうかが分かれる | 小さな修正と大きな追加を混ぜる | `delegation`、`flow_conformance` |
| 検査が一度で通らない | 既存のテストとぶつかる変更 | `check_pass`、`completion` |
| 触ってはいけないファイルの近くを変える | 検査の設定の隣のファイルを変える依頼 | `protected_untouched` |
| 依頼があいまいで、決め方が分かれる | 名前や置き場所を指定しない依頼 | `files_agreement`、`acceptance` |

## ホールドアウト

`H<番号>` の課題は、設計役・構築役・分析役に見せず、最後の評価だけで使う。改善が評価課題（T）に合わせすぎていないかを確かめるためである。T と同じ種類の、別の依頼にする（T の言い換えにしない）。

課題文と受け入れ条件の20字以上の行は、バンドルの検査で「評価課題の文をそのまま写していないか」に使われる。

## 良い例と悪い例

| | 依頼文 | 受け入れ条件 |
|---|---|---|
| 良い例 | 在庫から数を減らす関数を足して。在庫より多くは減らせないようにして | 在庫より多く減らそうとすると例外になる |
| 悪い例（答えを書いている） | `inventory.py` に `remove_stock(item, n)` を足し、`ValueError` を投げて、テストを `tests/test_inventory.py` に書いて | `remove_stock` がある |
| 悪い例（判定できない） | 在庫の処理をきれいにして | コードが読みやすい |
