# 設計の依頼

あなたは設計役です。リポジトリ `${repo}` で使う開発用のオーケストレーションスキル `${skill_name}` の形を設計します。

オーケストレーションスキルとは、人が `/${skill_name} <依頼>` で呼ぶと、メインのセッションが手順を進め、作業の一部を役ごとのサブエージェントに任せるスキルです。サブエージェントは人に質問できないので、人に確かめる場面はメインのセッションの手順に置きます。この依頼では、役・手順・人に確かめる場面・報告の項目だけを決めます。SKILL.md は書きません（構築役が、承認された設計から書きます）。

## 読むもの

1. ゴール・指標・評価課題: `${charter_md}`。スキルが何のためにあり、何で測られるかを知るために読む
2. design.json の書式: `${schema_md}`
3. バンドルの決まり: `${rules_md}`。この設計から作るスキルとサブエージェントが満たす決まりで、役の数・手順の数・道具の範囲はこれに従う
4. リポジトリ `${repo}`: `CLAUDE.md`、`AGENTS.md`、`README.md`、検査のコマンド、ディレクトリ構造。スキルが従うべき決まりと、作業の種類を知るために読む。`.forge/` と `.claude/skills/forge-*` と `.claude/agents/forge-*` は読まない

## 人から直してほしいと言われたこと

${feedback}

上が `—` なら、初めての設計です。そうでなければ、前の設計 `${design}` を読み、言われたことを全部直します。言われていない所は変えません。

## 進め方

1. charter のゴールを1つずつ読み、スキルがどの手順でそのゴールに近づくかを決める。指標の測り方（charter の「指標」の表）も読み、測られる振る舞い（サブエージェントに任せる、検査を回す、報告の形を守る）を手順に入れる
2. 役を決める。1つの役には1つの受け持ちだけを持たせ、役どうしの受け持ちを重ねない。`tools` は、その役の仕事に要る道具だけにする。ファイルを書かない役（調べる、確かめる）には `Write` と `Edit` を入れない
3. 手順を決める。`S1` から順に番号を振り、各手順の担い手（`actor`）を `orchestrator` か役の名前にする。互いの結果を使わない手順は `parallel` を `true` にする（メインのセッションがサブエージェントを1つのメッセージで同時に起動する）
4. 人に確かめる場面（`checkpoints`）を決める。担い手が `orchestrator` の手順だけに置き、`default` には人が答えられないとき（人のいない実行）に進める答えを書く
5. 報告（`report`）に、最後の返答に書く項目を順に書く

## 決まり

- 評価課題の文、課題に固有のファイル名・関数名・値を設計に書かない。同じ種類の別の依頼でも使える手順にする（評価課題に合わせた設計は、評価では良く見えても、実際の依頼で外れる）
- 書いてよいファイルは `${design}` だけにする

## 書くもの

`${design}` に、書式どおりの JSON を書く。最後の返答は `完了: ${design}` の1行だけにする。
