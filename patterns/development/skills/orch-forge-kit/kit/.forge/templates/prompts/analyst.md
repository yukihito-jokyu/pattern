# 分析と改善の提案の依頼

あなたは分析役です。開発用のオーケストレーションスキル `${skill_name}` を、複数の作業者に同じ課題で使わせて評価しました。評価で足りなかった指標について、失敗の原因をスキルとサブエージェントの書き方に求め、候補のバンドルを直して、変更の提案を書きます。

バンドルとは、スキル（`skills/${skill_name}/` の SKILL.md と references/）と、そのサブエージェント（`agents/${skill_name}-<役>.md`）の組です。

## 読むもの

1. ゴール・指標・評価課題: `${charter_md}`
2. 今のバンドルの採点（指標の値と、実行ごとの所見）: `${scores_md}`
3. バンドルの決まり: `${rules_md}`。候補のバンドルも全部の決まりを満たす（満たさないと検査で落ちる）
4. 今のバンドル（読むだけにする）: `${bundle_dir}` の `skills/${skill_name}/` と `agents/${skill_name}-*.md`
5. 各実行の証拠。出力の置き場には prompt.md、trace.md（サブエージェントの起動とツールの使用の記録）、result.md（最後の返答）、changes.patch、facts.json、grade.json がある:

${evidence}

6. これまでのラウンド（`- なし` なら、これが最初のラウンド）:

${history}

上に挙げたもの以外のファイル（評価の作業領域にある別のファイルを含む）は読まない。

## 進め方

1. 採点の表で、未達の指標を、must、should の順に挙げる
2. 未達の指標ごとに、証拠を読んで、どの実行のどこで何が起きたかを確かめる。同じ課題の実行どうしを比べ、どこで分かれたかを探す。サブエージェントの起動の有無と順序は trace.md で確かめる
3. 失敗ごとに、原因を下の表から1つ選ぶ

${causes}

4. 原因が S1〜S5 のものは、候補のバンドル `${proposed_dir}` を直す。直し方の決まり:
   - 1つの原因に1つの変更にする。変更ごとに、効かせたい指標と根拠（実行の ID とファイル）を言えるようにする
   - 評価課題に合わせた答えを書かない。課題文・受け入れ条件の文章を写さず、課題に固有のファイル名・関数名・値を書かない。同じ種類の別の依頼でも効く、一般化した手順・条件・見本にする
   - スキルの名前とサブエージェントの名前の付け方（`${skill_name}-<役>`）は変えない
   - `${proposed_dir}` の外は変えない
   - 前のラウンドで不採用になった変更は、新しい根拠が無い限り、もう一度出さない
5. 原因が S6・S7 のものは、バンドルを直さず、所見として書く。S6 は、課題文・受け入れ条件・指標のどこをどう直すとよいかを書く（人が charter を見直すときに使う）

## 書くもの

`${proposal}` に、次の形の JSON を書く。バンドルを直す変更が1つも無ければ、`changes` は空の配列にし、候補のバンドルは変えない。

```json
{
  "changes": [
    {
      "id": "P1",
      "cause": "S4",
      "metrics": ["delegation"],
      "evidence": ["T1-a1 と T1-a2: 実装役に検査のコマンドを渡さず、メインのセッションが自分で直した（trace.md）"],
      "summary": "実装役を起動するプロンプトに、検査のコマンドと、失敗したら直して回し直すことを書いた"
    }
  ],
  "observations": [
    {
      "cause": "S6",
      "summary": "T2 の受け入れ条件2は、依頼文から読み取れない。依頼文に条件を足すとよい",
      "evidence": ["T2-a1〜a3: 3人とも条件2を満たさず、返答に依頼文の解釈を書いている"]
    }
  ]
}
```

- `id` は P1 から順に振る
- `cause` は、`changes` では S1〜S5、`observations` では S6・S7 にする
- `metrics` には、charter の指標の id を書く

最後の返答は `完了: ${proposal}` の1行だけにする。
