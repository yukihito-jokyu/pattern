# 0002 オートフローを「準備＋依頼ごとのフロー」にし、検証済みの変更で止める

- 状態：採用
- 関係するルール：GATE-01、GATE-02、GATE-05

## 背景

指示は「プロジェクトのタスクやユーザーの要望から、人間がなるべく介入しないオートフローを作成するスキル」であり、AI が自走するため正しさを担保すること、参考の記事（Claude Code チームのコードレビュー）からフローの考え方と人が介入する場面を学ぶことが求められた。

記事の要点は、(1) 人の時間を最小にしつつリバートとインシデントを増やさない、(2) AI に検証手段を与えて出力を見せさせる、(3) 複数のエージェントの探索と投票で指摘を絞る、(4) リスクの段は変更が決め、AI の承認は人の承認に数えない、(5) ラウンドに上限を置く、(6) 人は「作るかどうか」「リスクの高いコード」「証拠を読むこと」「結果への責任」に残る、である（[research.md](../research.md) の記事の節）。

「オートフローを作成する」は、少なくとも3通りに読める。受付で、次の3点をユーザーに選んでもらった。

| 項目 | 選択肢 | 選んだもの |
|---|---|---|
| スキルの形 | 準備＋依頼ごとに組んで実行 / 依頼ごとに組んで実行のみ / プロジェクト専用のスキルを生成 | 準備＋依頼ごとに組んで実行 |
| 自走の終点 | 検証済みの変更で止める / 低リスクはコミットまで / PR・MR の作成まで | 検証済みの変更で止める（コミットは人の承認の後） |
| 入力元 | 文章 / Backlog / Redmine / GitLab・GitHub の Issue | 全部 |

## 選択肢

自走の正しさを何で守るかについて、次を比べた。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| スキルの文章で手順と関所を指示する | 作るのが速い | AI が関所を飛ばしても止まらない。条件の解釈が実行ごとに揺れる |
| Claude Code の Workflow で手順を固定する | 並列と順序をスクリプトで決められる | サブエージェントからは呼べず、人の関所（AskUserQuestion）を途中に挟めない。呼ぶたびに利用者の明示が要る |
| 補助 CLI が状態機械と関所を持ち、スキルは `status` に従うだけにする | 順序・証拠・投票・段・承認の結び付けを、テストできる Python のコードで決められる | 補助 CLI を作り、保守する費用がかかる |

## 決定

3つ目を採る。

- `autoflow-setup` がリポジトリごとに1回プロファイルを作り、人が承認する（H0）
- `autoflow` が依頼ごとに、計画の種類と予測の段から手順（`flow.json`）を組み、補助 CLI の `status` の指示で自走する。人は H1（条件付き）・H2（条件付き）・H3（毎回）でだけ判断する
- 終点は作業ブランチ上の検証済みの変更とし、コミットは H3 の承認の後、承認した tree と一致するときだけ行う。push はしない
- `autoflow-learn` が記録から人の介入とガードレールを数え、見逃しの発生源を直す提案をする

## 理由

記事の仕組みのうち、正しさに直結する部分（順序、証拠、投票、段、承認の結び付け、ラウンドの上限）は、AI の判断に任せると揺れる。補助 CLI のコードに置けば、テストと probe で効いていることを証明できる。

## 影響

- 関所の条件を変えるときは `policy.py` の表を変える（GATE-01）。スキルの文章は変えない
- 低リスクの変更を人の承認なしで取り込む運用（記事の「低」の段）にしたくなったら、H3 の扱いを `policy.TIERS` で段ごとに変え、`commit` の条件を変える。この ADR を置き換える
