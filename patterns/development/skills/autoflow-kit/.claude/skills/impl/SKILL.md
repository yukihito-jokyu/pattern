# autoflow-kit の実装手順

このスキルは次の資料と一緒に使う。パスは基盤のルートからの相対パスである。

- `docs/design/rules.md`：ルールの全文。`<接頭辞>-<番号>` のルールIDで参照する
- `.claude/skills/impl/references/patterns.md`：パターンごとの手順と、作るファイルの一覧
- `docs/design/architecture.md`：依存の許可表（4章）と変更シナリオ表（7章）
- 見本（参照実装）：`kit/.autoflow/autoflow_kit/`（全モジュール）、`kit/.autoflow/templates/prompts/`、`tests/`

既存のコードと rules.md が食い違ったら rules.md に従い、食い違いを報告に書く。

## 1. 依頼をパターンに振り分ける

| 依頼に含まれること | patterns.md の節 |
|---|---|
| H1（方向の確認）・H2（行き詰まり）を起こす条件、関所の選択肢 | 1 |
| リスクの段の決め方（パス、行数）、レビューの深さ・観点・投票の閾値 | 2 |
| 取得元（課題の管理の道具） | 3 |
| プロファイル（profile.json）の項目 | 4 |
| サブエージェントが書く JSON の項目、ひな形の置き換えの名前 | 5 |
| 既存のサブコマンドへの引数、既存の段の振る舞い | 6 |
| 新しい段・サブコマンド | 7 |
| プロンプトの文言、配布するスキルの手順、サブエージェントの定義 | 8 |
| 不具合の修正（振る舞いを変えずに直す） | 9 |
| 道具の版（ruff、mypy）を上げる | 実装しない。ADR を書いてから `Makefile` の `RUFF`・`MYPY` を変える（PROC-03） |

- 複数の行に当たる場合は、表の上から順に全部行う
- どの行にも当たらない場合は、実装しない。必要なパターンとルールを提案として報告する。見本に無い形をその場で発明すると、作者ごとに違う形が生まれるからである

## 2. 依頼から決まらない値

推測で決めない。聞ける状況ならユーザーに聞く。聞けない状況なら既定値で決め、報告の3に書く。

| 決めること | 何に響くか | 既定値 |
|---|---|---|
| 規則・観点・取得元・段の名前 | 定数、JSON、`test_<名前>` のメソッド名 | 依頼の語を英語の snake_case にした名前（取得元は小文字1語）。規則は判定の関数名（`_is_<状態>`・`_has_<もの>`）だけを決め、id はそこから `_is_`・`_has_` を除いて `h1_`・`h2_` を付ける（GATE-01。`_is_human_only` → `h1_human_only`） |
| 規則の文（`PlanRule`・`ProgressRule` の text） | gates.md、関所の理由のファイル | 既存の規則と同じ「〜である」「〜した」で終わる1文 |
| プロファイルの新しい項目の既定値 | 既存の利用者の振る舞い | 今の振る舞いを変えない値。上限なら既存の上限と同じ桁 |
| 新しい観点を入れる深さ | 探索役の人数と費用 | `deep` だけに入れる |
| 取得元が課題の番号（ref）を要るか | `start` の検証 | 課題の番号のある道具なら要る（`True`） |
| JSON の新しい項目の型と、無いときの値 | ひな形の例、`support.act_*` | 文字列なら `""`、一覧なら `[]`。省略は許さず、必須の項目にする |
| 人に見せるエラーの文言 | 出力、テストの assert | 「<何が>…です。<次にすること>」の2文。次にすることは命令形で書く |
| 新しいサブコマンドの名前 | `cli.HELP`、`status`、スキルの表 | `<段>-new`（プロンプトを書く）と `<段>-check`（出力を確かめる）の組か、動詞1語 |
| 新しいテストのメソッドを置く場所 | 差分の位置 | そのテストのクラスの最後 |
| プロンプトの一覧の1行を作る関数の名前 | 段のモジュールの関数名 | `_<置き換えの名前>_line`（`prior_findings` → `_prior_findings_line`、`findings` → `_findings_line`）。値を作る段のモジュールに置く |

## 3. 書く前に読む

1. patterns.md の該当する節を最後まで読む
2. rules.md のうち、パターンに対応する接頭辞の節をすべて読む

   | パターン | 読む接頭辞 |
   |---|---|
   | 1、2 | GATE、TEST、PROC |
   | 3、4、5、6 | STATE、ERR、NAM、TEST、PROC |
   | 7 | 全部 |
   | 8 | STATE、GATE、OPS、STR |
   | 9 | CODE、ERR、TEST |

3. 見本の該当ファイルを開き、構成・命名・import の並び・コメントの書き方を確かめる

## 4. 作る順序

patterns.md の該当節の「作る・変えるファイル」の順に作る。段を足すときは PROC-01 の順（`trail` → `contracts`・`layout` → 段のモジュール → `status` → `cli` → テスト → `autoflow/SKILL.md`）に作る。

変えるのは、当たった節の「作る・変えるファイル」の表にあるファイルだけにする。表のモジュール（「項目を使う段のモジュール」のように行で名指ししたものを含む）を変えたら、そのテスト `tests/test_<モジュール>.py` も表にあるものとして扱い、変えた振る舞いを確かめる assert を足す。表に無いファイル（設計文書、README、他の段のモジュールなど）を変えたほうがよいと考えたら、変えずに報告の5に書く。表の外の変更は、作者ごとに入れるかどうかが分かれるからである。

各ファイルを保存するたびに、hooks が `make fix-file` を走らせる（TOOL-02）。指摘が出たら、次のファイルに進む前に直す。表（`policy` の表、`profile.FIELDS`）を変えたら `make docs` を回す。

## 5. 検証する

1. `make check` を実行する
2. 落ちたら、エラーに出たルールIDか lint のルール名を rules.md で引き、コードを直す。lint のルール名とルールIDの対応は `docs/design/enforcement-matrix.md` にある
3. 次の方法で検査を黙らせない
   - 検査の設定や保護ファイルを変える
   - 抑止コメントを書く
   - テストを skip する、または消す

   どうしても直せない場合は、その状態のまま報告する

## 6. 完了前チェックリスト

該当するファイルを開き、1つずつ確かめる。

- [ ] PROC-02：rules.md の波及の対応表で、変えた左の列に対応する右の列を全部変えた（`policy` の表 ⇔ `make docs`、`policy.LENSES` ⇔ `finder.md` の観点の節、`contracts` の項目 ⇔ ひな形の例と `tests/support.py`、`profile` のキー ⇔ `views.render_profile` と `setup.py`、`layout.SOURCES` ⇔ `references/sources.md`、`trail` の段 ⇔ `status.py` と `autoflow/SKILL.md`、モジュールの増減 ⇔ `structure_check.py` と architecture.md の許可表）
- [ ] TEST-03：足した名前ごとに、rules.md の表の置き場に `test_<足した名前>` を1つ足した。名前を足さない修正は、既存のメソッドに assert を足した
- [ ] STATE-01：段の進み具合（何回目か、どの段か）を `trail.jsonl` 以外のファイルに書いていない
- [ ] STATE-02：プロンプトの文をコードに書いていない。置き換えの値は生の値か `render.bullets`・`render.table` の結果だけ
- [ ] NAM-02：関数名の先頭の動詞を rules.md の語彙表の意味で使った。真偽値を返す関数は `is_`・`has_` で始めた
- [ ] CODE-01：引数の `dict`・`list` を変えていない（`problems` を除く）
- [ ] OPS-03：人に見せる文言は日本語で、表と数は `render` の関数で書いた
- [ ] PROC-06：profile.json のキーを足す・消す・意味を変えたなら、`SCHEMA_VERSION` を上げ、ADR に移行の手順を書いた
- [ ] TOOL-04：保護ファイルを変えていない（依頼で明示されたときを除く）
- [ ] `make check` が通った（PROC-05）

## 7. 報告する

次の順で書く。

1. 何を作ったか（使ったパターン）
2. 変えたファイルの一覧（作る順序の順）
3. 2 で決めた値と、その根拠（依頼文、ユーザーの回答、既定値のどれか）
4. `make check` の結果（出力の末尾）
5. 決めきれずに残したこと、ルールと既存コードの食い違い
