# autoflow

依頼を受け取り、人の関所以外では人に聞かずに、検証済みの変更と報告書まで進める。

## このスキルの考え方

AI が自走するので、正しさは AI の自己申告ではなく仕組みで担保する。順序と判定は補助 CLI（`python3 .autoflow/autoflow.py`）が実行の記録から決め、このスキルは CLI の `status` の指示に従うだけにする。

| 担保すること | 仕組み |
|---|---|
| 「できました」を証拠にしない | 検査コマンドは CLI の `verify` が自分で実行し、作業ツリーの版（tree）に結び付けて記録する |
| 関所を飛ばさない | 各サブコマンドは、記録から求めた今の段でなければ動かない |
| レビューの雑音を減らす | 観点ごとの探索役が並列に探し、別の検証役の票が閾値以上の指摘だけを残す。2ラウンド目からは差分だけを見る |
| リスクは作者でなく変更が決める | 差分のパス・行数から規則で段を決め、判定役は段を上げる方向にだけ効く |
| 人の承認は人だけのもの | 人の回答の原文と tree を記録し、承認した tree のままのときだけコミットする |

関所の条件と表は [references/gates.md](references/gates.md) にある。

## 始め方

1. 引数が `resume <実行の id>` なら、start をせずに「繰り返すこと」へ進む
2. 引数から取得元を決め、[references/sources.md](references/sources.md) の表のとおりに、依頼の題名・本文・コメントを取る
3. 取った内容を `.autoflow/runs/intake.md` に Write で書く（題名、本文、コメントをそのまま。要約しない）
4. `python3 .autoflow/autoflow.py start --source <種類> --ref <番号> --url <URL> --title '<題名>' --body-file .autoflow/runs/intake.md` を実行する。番号と URL が無い取得元では、その引数を省く
5. 出力の「実行:」の id を覚え、「繰り返すこと」へ進む

start が `エラー:` で落ちたら、エラーの全文を人に見せて止まる（プロファイルの承認が無い、作業ツリーがきれいでない、など。直すのは人である）。

## 繰り返すこと

`python3 .autoflow/autoflow.py status --run <実行の id>` を実行し、出力の各行を書き出しで読み分けて、次の表のとおりにする。1つ終えたら、また status から始める。

| 行の書き出し | すること |
|---|---|
| `対象:`・`段階:` | 読むだけ。段階を人への途中の報告に使う |
| `次: <コマンド>` | そのコマンドを Bash で実行する。`verify` は検査コマンドを全部回すので、Bash の timeout を 600000 にする |
| `次: 下の job を…` | 続く `job` の行を全部、1つのメッセージの Agent ツールの呼び出しにして並列に起動し、全員の返答を待つ |
| `job <エージェント> <ラベル> <プロンプトのパス>` | Agent ツールの subagent_type を `<エージェント>`、description を `<ラベル>`、prompt を「`<プロンプトのパス>` を読み、書かれたとおりに作業する」にする。プロンプトの中身を書き換えたり要約したりしない |
| `その後: <コマンド>` | job が全部終わってから、そのコマンドを実行する |
| `人:`・`選択:` | 「人に確かめること」に従う |
| `終了:` | 「最後の報告」をして終える |
| `WARN ` | 人への報告に含める |

段と、段を受け持つサブコマンドと役は次のとおりである。

| 段 | サブコマンドの順 | 起動する役 |
|---|---|---|
| verify | `verify`（作業の前、再現のテストの後、実装の後） | なし |
| plan | `plan-new` → `plan-check` | autoflow-planner |
| decide | `decide`（人の回答の原文を渡す） | なし（人） |
| build | `build-new` → `build-check` | autoflow-builder |
| risk | `risk-new` → `risk-check` | autoflow-risk |
| review | `review-new` → `review-collect` → `review-tally` | autoflow-finder（観点ごと）、autoflow-verifier（人数ぶん） |
| handoff | `handoff` | なし |
| commit | `commit` | なし |

## サブコマンドが `エラー:` で落ちたとき

| エラーの中身 | すること |
|---|---|
| `<ファイル> に N 件の問題があります`（サブエージェントの出力の検証） | 直前の job を、エラーの全文を添えて起動し直す（prompt に「前の出力に次の問題があった。プロンプトを読み直し、出力を書き直す」とエラーの全文を足す）。終わったら同じサブコマンドをやり直す。同じ段で2回直らなければ、人に報告して止まる |
| `読み取りだけの役の間に作業ツリーが変わりました` | 何も直さずに、人に報告して止まる |
| `今は X の番ではなく Y の番です` | status からやり直す |
| それ以外 | エラーの全文を人に報告して止まる |

## してはいけないこと

- status の出力に無いコマンドを実行する。順序を自分で決める
- 自分でコードを直す。コードを変えるのは実装役だけである
- サブエージェントの返答の本文で判断する。判断は CLI がファイルから行う
- git の commit・push・reset・checkout・stash を自分で実行する。コミットは `commit` サブコマンドだけが行う
- `.autoflow/` の下のファイル（記録、プロファイル、プロンプト、出力）を手で書き換える
- 検査を通すために、検査の設定やテストを緩めるよう実装役に頼む

## 人に確かめること

人の関所は、status の `人:` と `選択:` の行で示される。関所の意味は [references/gates.md](references/gates.md) にある。

1. `人:` の行のファイルを Read で読み、人がそのファイルを開かなくても決められるように要点を示す。ファイルのパスも示す
   - H1（方向の確認）：ゴール、範囲、受け入れ条件、依頼から決まらなかった値、当たった条件
   - H2（行き詰まり）：当たった条件、今の状況、直前の検査の失敗やレビューの指摘
   - H3（最終承認）：「H3 で人がすること」、証拠、検査が見ていないこと、レビュー、コミットの案
2. AskUserQuestion で、`選択:` の行の選択肢（選択の名前と意味）を出して選んでもらう。直してほしいことは、選択肢の補足の文章で受け取る
3. 選ばれた `選択:` の行のコマンドの `'<人の回答の原文>'` を、人の回答の原文（選んだ選択肢と、書かれた補足をそのまま）で置き換えて実行する

回答が無い・空・自動で閉じた質問は、承認にも選択にもしない。関所のファイルの場所を報告して止まる。

AI の推奨を添えてよいが、推奨を人の回答の代わりにしない。H3 の段が high なら、2人目のレビューを頼むかも聞く。

## 最後の報告

- コミットした：コミットの id、作業ブランチ、報告書のパス、push はしていないこと
- 止まった：止まった段と理由、関所のファイルのパス、再開の方法（`/autoflow resume <実行の id>`）
- どちらでも、人の関所の回数と、依頼から決まらなかった値（報告書の「検査が見ていないこと」）を書く
