# 業務からモデルを選ぶ

## 概念図と設計図を分ける

概念モデルは、対象業務を理解するために概念・属性・関連を表す。Larmanの[Domain Modelsの公開プレビュー](https://www.oreilly.com/library/view/applying-uml-and/0130925691/0130925691_ch10lev1sec2.html)は、この分析の視点を説明している。公開プレビューで確認できない章の内容まで読んだものとして引用しない。

設計モデルでは、業務の振る舞いと責務も検討する。[FowlerのDomain Model](https://martinfowler.com/eaaCatalog/domainModel.html)はデータと振る舞いを含むモデルを扱う。概念図の箱を、そのまま実装クラスやDBテーブルへ一対一で変換する必要はない。

## 具体的な業務から概念を見つける

「会員が注文を確定し、出荷確定前にキャンセルを要求する」のように、対象を具体的な出来事へ分解する。[Domain Storytelling](https://domainstorytelling.org/quick-start-guide)の、誰が・何を・何に対して行うかをたどる視点も使える。手法の実施そのものを必須にせず、必要な業務の理解を得る。

名詞だけで箱を増やさず、独立して扱う理由を確かめる。例えばキャンセルが単なる注文状態の変更なら振る舞いの候補になる。申請者・承認者・審査履歴を別に管理するなら、キャンセル申請を独立した概念にする理由がある。注文状態は、状態ごとに独立したライフサイクルを管理する要件がなければ、まず注文の属性として扱える。

属性も具体例から選ぶ。商品の現在価格が変わっても、過去の購入額を変えてはいけないなら、注文明細に購入時単価が必要になる。名前が似ていても、時点や業務上の意味が異なる値を一つにまとめない。

## 関連と多重度を読む

関連名は「顧客は注文する」「注文は明細を含む」のように読む。概念間の構造的な関連に、時間順や処理依存の矢印の意味を混ぜない。通常の関連は実線とし、ナビゲーション方向や合成を示す必要がないなら矢印・ひし形を足さない。

多重度は、反対側の1つの対象に対して何個あるかを端に書く。例えば顧客側の `1` と注文側の `0..*` は「1件の注文の顧客は1人」「1人の顧客の注文は0件以上」を表す。未注文の会員、初回注文、複数注文という具体例を使って両方向を確かめる。

| 記法 | 個数 |
| --- | --- |
| `1` | 必ず1つ |
| `0..1` | 0または1つ |
| `0..*` | 0個以上 |
| `1..*` | 1個以上 |

要件が不明な多重度には短く「未決」を付け、仮に置くなら根拠と影響を図外の判断メモへ書く。見栄えをそろえるために全関連を1対多にしない。

## ルールから責務と境界を検討する

不変条件は、業務上成立していなければならない条件である。「出荷確定済みの注文をキャンセル済みにしない」のように、禁止する状態と操作で表す。設計図では、その条件を誰がどの範囲で守るかを対応付ける。[Vernonの集約設計](https://www.informit.com/articles/article.aspx?p=2020371&seqNum=2)は、真の不変条件に基づき整合性の境界を決める理由を説明している。

Entityは同一性とライフサイクルを追う対象、Value Objectは値の同等性で扱う対象として候補を検討する。例えば購入時単価を通貨と金額の組で扱う理由があれば、Moneyという値の候補を示せる。ただし、数量・価格という名詞だけから専用クラスを必ず増やすわけではない。

注文と明細を同じ集約に置くかは、変更時に何を同時に正しく保つ必要があるかで検討する。返金を別の決済モデルへ依頼する案では、注文キャンセルの成立と返金完了を別の事実として扱い、同期・非同期、失敗時の再試行、二重依頼の扱いを業務要件から決める。作図だけでトランザクション実装や競合対策を決定済みにしない。

[Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)はモデルと言葉が意味を持つ範囲を明確にする。カタログの商品と注文内の購入商品情報、在庫管理の商品を、一つの巨大モデルへ統合する必要はない。これは集約境界の話とは異なり、別サービス化を自動的に要求するものでもない。

## 具体例で不足を見つける

ルールごとに、入力となる状態・操作・期待結果を記す。[Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/)のように、ルール、具体例、質問を分けると、理解の食い違いを見つけやすい。

注文なら「価格変更後も購入時単価が残る」「出荷とキャンセルが競合する」「返金だけ失敗する」「同じキャンセルを再要求する」を当てはめる。答えが入力にない場合は、期待結果を発明せず、判断が必要な質問とする。単純な業務には必要な概念だけを残し、図の細かさを品質の代わりにしない。

これらの具体例や判断理由はMarkdownで説明し、ページ名と要素名を使って図に対応付ける。図への補足が必要なら、例えば集約候補は包含する境界、キャンセル条件は遷移の短いガードとして表す。目的や範囲、ルールの説明文を図の中へ並べることは、ドメインの構造を表す代わりにはならない。
