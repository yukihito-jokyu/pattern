# 注文キャンセルのモデル例

`order-cancellation.drawio.png` は、学習用の仮定から作った3ページの例である。PNGの見た目は「概念モデル」だが、draw.ioで開くと「設計候補」「注文状態遷移」も再編集できる。実際の注文業務の確認済み要件ではない。

図にはモデルの要素を描き、目的・範囲・記法の読み方・仮定・判断理由・未決事項はこのMarkdownで説明する。以下の説明は、ページ名と要素名で図を参照する。

## 目的・範囲と用語

注文キャンセルが成立する条件と、それに必要な概念を整理する。対象は会員の注文確定後から出荷確定まで。返品、会員登録、配送業者の内部処理は対象外とする。ここでの「出荷確定」は、倉庫作業の開始や配送業者への引き渡しとは区別し、キャンセルを禁止する業務上の境界として仮に置く。実業務では、どの出来事を指すか確認が必要になる。

学習用の仮定は次の4つである。

- A1：確定した注文は1人の会員が行い、会員は注文を0件以上持つ。
- A2：確定した注文には明細が1件以上あり、明細は1件の注文に属する。
- A3：明細は1つの商品を対象とし、商品は明細に0回以上現れる。
- A4：購入時単価は注文確定時に保持し、その後の現在価格の変更で変わらない。

## ページと記法の読み方

「概念モデル」は顧客・注文・注文明細・商品の構造を示す。箱の上段は概念名、下段は属性であり、実線が関連、線上の語が関連名である。端の多重度は、反対側の1件に対する個数を示す。`1` は必ず1つ、`0..*` は0個以上、`1..*` は1個以上を意味する。

「設計候補」は責務と整合性の境界を検討するページである。「注文集約（候補）」の破線の囲みは、Order・OrderItem・Moneyを同じ候補範囲に含むことを示す。EntityとValue Objectは箱の見出しにも記し、色だけで役割を区別しない。Orderへ破線で結び付いた短い制約ノートは、出荷確定後のキャンセルを禁止する不変条件の担当を示す。図の右へ向かう破線矢印は、決済済みの場合にPaymentへ返金を依頼する連携候補であり、実装方式は決めていない。

「注文状態遷移」は注文確定・出荷確定済み・キャンセル済みの状態と、許可した変化を示す。角丸の箱が状態、矢印が遷移、線上の語が操作である。`[出荷確定前]` はキャンセル操作のガードを表す。出荷確定済みからキャンセル済みへの矢印はない。二重要求や競合などの未決事項は、推測した遷移を描かず、このメモのQ1〜Q4へ残す。

## 概念と関連の根拠

「顧客」は会員番号で会員を識別し、「注文」は注文番号と状態で注文の経過を追う。「注文明細」は対象商品・数量・購入時単価の組で購入内容を記録するため独立させる。「商品」は注文とは別に商品名と現在価格を変更できる対象である。状態はこの例では注文の属性とし、状態ごとの独立クラスは増やさない。

顧客―注文の関連「注文する」は顧客側が `1`、注文側が `0..*` でA1に対応する。注文―注文明細の「明細を含む」は注文側が `1`、明細側が `1..*` でA2に対応する。注文明細―商品の「対象商品」は明細側が `0..*`、商品側が `1` でA3に対応する。線の左右を入れ替えても、この読み方は維持する。

商品の現在価格を1,000円から1,200円へ変えても、購入時単価1,000円・数量2の明細の金額は2,000円のままである。A4を満たすため、商品の現在価格を過去の注文金額の計算元にはしない。

## ルール・具体例・未決事項

| ID | 学習用ルールまたは質問 | 状態・操作の具体例 | 結果と対応箇所 |
| --- | --- | --- | --- |
| R1 | 出荷確定前はキャンセル可能と仮定する | 注文確定後、出荷確定前に要求する | キャンセル済みへ。状態遷移ページのキャンセル線 |
| R2 | 出荷確定後はキャンセル不可と仮定する | 出荷確定後に要求する | 拒否。出荷確定済みからのキャンセル線は描かない |
| R3 | 決済済みのキャンセルには返金が必要と仮定する | 決済完了後、出荷確定前に要求する | キャンセル成立と返金完了を分ける。設計候補ページの決済への連携 |
| Q1 | 再キャンセル要求の応答を決める必要がある | キャンセル済みの注文に再要求する | 同じ結果を返すか拒否するか未決。状態を二重に変更しない |
| Q2 | 出荷確定とキャンセルの競合をどう扱うか | 2つの操作が並行して発生する | どちらを成立させるか、整合性の保証方法は未決 |
| Q3 | 返金だけ失敗したらどうするか | キャンセル成立後に決済処理が失敗する | 再試行、担当者対応、通知の要件は未決。返金失敗で注文を自動的に戻すと仮定しない |
| Q4 | 在庫引当の解放が必要か | キャンセルが成立する | 在庫業務の範囲と連携条件は未決 |

## 設計候補と境界

設計候補ページでは、Orderを同一性と状態を持つEntity・集約ルート候補にする。キャンセル可能性の判断と「出荷確定済みはキャンセル状態にしない」というR2の不変条件を担当させる。OrderItemは数量と購入時単価を注文の一部として扱う候補であり、確定注文の明細を1件以上保つA2を同時に守る必要があるなら、同じ集約にする理由になる。単に親子関係だから境界を決めたのではない。

購入時単価はMoneyというValue Objectの候補として、金額と通貨を一組にする。ただし、通貨の要件はこの例では未決であり、業務に不要なら専用の型を増やす理由にはならない。

Paymentは決済・返金固有の状態を扱う別の管理対象候補である。アプリケーションは注文の取得・キャンセル要求・保存・必要な返金依頼を調整する。図の破線はこの連携の候補であり、同期か非同期か、トランザクション方式、APIを決める線ではない。

この図は注文管理の視点である。商品カタログや在庫管理のモデルは対象外であり、同名の商品を一つの巨大なモデルへ統合する意図はない。コンテキストの境界を、集約やマイクロサービスの境界と同一視しない。

## 確認方法

配布ルートから次を実行すると、PNGと埋め込まれた全3ページの構造を検査する。

```sh
python3 skills/drawio-domain-model/scripts/validate_drawio.py examples/order-cancellation.drawio.png
```

各ページをCLIで一時PNGへ書き出して、画像の文字と線を確認する。利用者が希望する場合などは、追加でdraw.ioのGUIでコピー上の編集・保存・再読み込みを確かめる。構造検査だけでは、業務ルールの承認や文字の読みやすさを確認したことにならない。
