# 0003 標準ライブラリ flag の上に、名詞・動詞のサブコマンドの枠組みを internal/cli として作る

- 状態：採用
- 関係するルール：OPS-05、OPS-06、CODE-02、STR-04、NAM-04、NAM-06、ERR-01、ERR-04

## 背景

CLI の引数の解析には、ユーザーの指示で標準ライブラリの `flag` を使うことが決まっている（指定による）。`flag` はフラグの解析だけを持ち、次の機能を持たない（[research.md「flag」](../research.md#flaggo-標準ライブラリgo-1272-に同梱)）。

- サブコマンド（`go-cli task add`）
- フラグを位置引数の後ろに書くこと（`flag` は最初の位置引数で解析を止める）
- ヘルプの整形、`--json` の共通化、エラーの種類から終了コードへの変換

これらを各コマンドが自分で書くと、ヘルプの形、`--json` の有無、終了コードがコマンドごとに分かれる。

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 各コマンドが `flag.NewFlagSet` を直接使う | 枠組みが要らない | 解析・ヘルプ・出力・終了コードの書き方がコマンドの数だけ生まれる |
| 外部の CLI ライブラリ（cobra など） | 機能がそろっている | 指示（`flag` を使う）に反する。DEP-04 と衝突する |
| `flag` の上に小さな枠組みを `internal/cli` として作る | 解析・ヘルプ・出力・終了コードを1か所で決め、型で縛れる | 枠組みのコードを保守する必要がある |

コマンドの形についても、`go-cli add-task`（動詞と名詞を1語にする）と `go-cli task add`（名詞・動詞の2段）を比べた。clig.dev は `noun verb` の形が一般的で、名詞が違っても同じ動詞を使うことを勧めている。

## 決定

- `internal/cli` に `App`（ツール全体）・`Group`（名詞）・`Command`（動詞）の3つの型を置き、コマンドは常に `go-cli <noun> <verb> [args] [flags]` の2段にする
- `cli.Command.Run` の型を `func(ctx context.Context) (cli.Output, error)` にし、コマンドが書き込み先と終了コードを選べないようにする（OPS-05）
- `--json` と `--help` は枠組みが全コマンドに付ける。`--json` なら出力型を JSON に、そうでなければ `WriteText` で文章に書く
- フラグの解析は `flag.FlagSet` を `ContinueOnError` で使い、最初の位置引数で止まったら位置引数を1つ取り除いて解析を続ける。こうしてフラグを位置引数の前後どちらにも書けるようにし、`--` の後ろはすべて位置引数として扱う
- 位置引数は `cli.Arg{Name, Value}` で宣言し、数が合わなければ枠組みが入力の誤り（終了コード2）にする
- 終了コードは `errkind` のエラーの種類から枠組みが決める（0：成功、1：想定外の失敗、2：入力の誤り、3：見つからない）

## 理由

コマンドの書き方を1通りにするには、コマンドが選べることを減らすのが最も確実である。`Run` の型を絞れば、出力先や終了コードをコマンドが書く余地は型の段階で無くなり、文書やレビューに頼らずに済む。外部のライブラリを使わずに済むのは、必要な機能（2段のサブコマンド、ヘルプ、JSON、終了コード）が小さく、`flag` の上に数百行で作れるからである。

## 影響

- 楽になること：サブコマンドを足す作者は、`<verb>.go` の5つの宣言を書くだけでよい。ヘルプ・`--json`・終了コード・`docs/cli.md` は自動でそろう
- 難しくなること：短いフラグ（`-a`）、フラグの別名、3段以上のサブコマンド、補完の生成は作れない。必要になったら枠組みを広げる ADR を書く
- 変えたくなったとき：`internal/cli` を変え、`internal/cli/cli_test.go` と全サブコマンドのテストを通す。`Run` の型を変える場合は全 `<verb>.go` と STR-04 の構造検査が変わる
