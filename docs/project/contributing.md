# パターンの追加・更新

パターンは説明と実装を一組で管理します。文書では設定値や構造の意味を理解できるようにし、ZIPには利用・検証に必要なファイルをそろえます。

## 配置を決める

`<分野>/<分類>/<パターン>`の3階層を決め、説明と実装の両方に同じパスを作ります。名前は英小文字を基本に、複数語はハイフンでつなぎます。数字は先頭以外で使えます。

```text
docs/<分野>/<分類>/<パターン>/
  index.md
  images/                 # 必要な説明用PNGがある場合だけ作る
patterns/<分野>/<分類>/<パターン>/
  README.md
  ...                     # コード・設定・依存関係・検証ファイル
```

追加手順などの運用文書は`docs/project/`に置き、対応実装を要求しません。分野名に`project`を使わないでください。

プロジェクト直下の`scripts/`は、配置確認・文書検証・ZIP生成などプロジェクト全体の共通処理に限定します。個別パターン専用のスクリプトは`patterns/<分野>/<分類>/<パターン>/`内に置き、ZIP単体で実行できるようにします。ルートから実行することやCIで使うことだけでは、共通処理にはなりません。追加前に既存の共通処理や対象ツールのコマンドで対応できるか確認します。

プロジェクト直下の`tests/`も、管理処理や掲載サイトなどプロジェクト全体の共通機能を確認するテストと、その補助処理・fixtureに限定します。個別パターン専用のテストは対象パターン内に置き、ZIPに含めます。共通機能のテストには検証用fixtureを使い、特定の実用パターンの文言・設定・収録ファイルに依存させません。

## 文書と実装を作る

[文書テンプレート](./templates/index.md.template)を文書側の`index.md`へ、[READMEテンプレート](./templates/README.md.template)を実装側の`README.md`へコピーします。記入欄はすべて具体的な説明に置き換えます。

最初に何のパターンかを説明し、全体構造と主要ファイルの役割を示します。中心部分では、意味のまとまりごとにコードを示し、指定の意味、実際の入力と結果、他のファイルや処理との関係、採用理由を説明します。設定は親キーも含め、対象箇所が分かる形にします。

READMEはZIP単体で読む手順です。サイトの説明を複製するより、環境・依存関係・配置先・実行場所・コマンド・期待結果を明確にします。利用先で変更する値があれば、変更箇所と例を示します。

設定台帳とsetupスキルを用意する場合は、台帳の網羅性を保ちながら、質問項目を「重要」「普通」「あまり見なくてよい項目」に分類します。開始時に「重要のみ」「重要＋普通」「すべて」を選べるようにし、範囲外は現在値・未設定時の既定動作を維持します。省略を個別確認済みと混同せず、範囲外を変更するときには追加確認が必要になるよう、スキル・CLI・回答検証をそろえます。

検証には対象の言語・ツールに合ったコマンドを使い、必要なテスト・設定ファイルを実装側に含めます。テスト本体の名前は統一しません。パターンのルートに`ci.json`を置き、準備・検証コマンドと必要な実行環境を指定します。共通CIが自動的に対象へ追加するため、パターンごとのCIジョブ追加は不要です。READMEに環境確認、依存関係の導入、検証の手順と期待結果を書き、準備に失敗したら停止します。詳しくは[検証とZIP配布](./verification.md)を参照してください。

## トップページの紹介情報

トップページの一覧は、各パターンの`index.md`から自動生成します。タイトル・説明は`title`・`description`、文書へのリンクは`slug`、カテゴリ名は上位ディレクトリの`_category_.json`の`label`を使います。カテゴリ名の指定がなければディレクトリ名を表示します。ZIPのURLはパターンIDから生成するため、一覧用に書き直す必要はありません。

一覧だけで表示する特徴や画像は、文書先頭の`pattern`に指定します。

```yaml
title: HTTP APIのエラー処理
description: 入力不備と内部エラーを分けて応答する構成。
slug: /backend/api/error-handling
pattern:
  position: 1
  actionLabel: 構成と処理の説明
  features:
    - label: 応答
      value: エラー種別ごとのHTTPステータス
```

`pattern`は省略できます。省略時もタイトル・説明・説明へのリンク・ZIPを表示し、説明ボタンは「詳しい説明を読む」とします。`position`は小さい順で、省略時は0です。同じ値ならID順に並びます。`features`は`label`と`value`の配列で、ラベルの重複は認めません。

画面例が必要なら、`pattern`の中に次を追加します。

```yaml
  preview:
    src: ./images/screen.png
    alt: 左にナビゲーション、中央に説明本文を配置した画面
    width: 1440
    height: 1100
    caption: 文書画面の例
    anchor: 完成画面
```

`src`は同じ文書の`images/`配下のPNGです。`alt`・`width`・`height`・`caption`を指定します。画像を押すと説明文書へ移動し、`anchor`があればその見出しへ移動します。不要なら`preview`全体を省略します。

文書と対応実装を追加・削除すると、次のビルドで一覧も更新されます。`draft: true`または`unlisted: true`の文書は一覧に載せません。トップページのTSXへパターンを追記する作業は不要です。公開済みの`slug`を変える場合は、従来どおり参照元への影響を確認します。

## 画像とダウンロード

説明に必要な画像は`images/<内容が分かる名前>.png`に置き、`![処理の流れ](./images/flow.png)`のように参照します。PNG以外を改名しただけでは通りません。コード例で十分なら画像は不要です。

ZIPリンクには`/downloads/patterns/<分野>/<分類>/<パターン>.zip`を指定します。

```md
[実装をダウンロード](/downloads/patterns/backend/api/error-handling.zip)
```

これは配置例です。ZIPはビルド時に生成されるため、手動で圧縮・配置・コミットしません。カテゴリ表示名や順序は必要な階層の`_category_.json`に指定します。サイドバーへ文書IDを手作業で追加しません。

## 確認して結果を残す

ルートで実行します。

```sh
npm run check:dir
npm run check:docs
npm test
npm run typecheck
npm run build
npm run test:e2e
```

個別パターンはZIPを別の場所へ展開し、READMEの準備・検証手順で確認します。

`npm run serve`で自分の文書へサイドバーから移動し、本文・PNG・ZIPと、取得したZIPのREADMEを確認します。E2Eのサンプル成功だけで、自分の文書をレビューしたことにはしません。

確認日・環境・期待結果・実際の結果・未確認事項を文書に残し、[レビュー項目](./review.md)を確認します。失敗・未実施・人間の確認待ちは成功と区別します。

更新では説明・実装・例・検証結果を併せて見直します。削除・改名では両側と参照元を更新し、再生成で古いZIPが消えることを確認します。
